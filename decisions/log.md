## 2026-09-30 — Ctrl+C при записи токена: лечить корень
- **Решение человека:** «Лечить корень сейчас» (рекомендация Юрки).
- **Контекст:** третье микросекундное окно одного класса (Ctrl+C в `vault._timed`: ожидание → старт потока (F-1) → ветка таймаута, плюс двойное прерывание). Правило «один баг > 2 раз = долг процесса»: окна по одному больше не латаем.
- **Что:** на время записи токена в хранилище (до 15 с) SIGINT откладывается и срабатывает сразу после критической секции — закрывает все окна, включая двойное нажатие. Не брать вариант Astra «не снимать SS-ссылку в `finally`» — на машине без SS даёт вечное «Выход не завершён».

## 2026-10-15 — REMOTE-LIMITS A3: уточнения к тестам (решение Юрки, технические)

1. П7, `nextAt`: будущий `nextAt` — норма. Чужая запись не свежая для B2, если `nextAt > now + interval + 60`. `interval` берётся из чужого `schedule`, если он в {900, 1800, 3600, 14400}, иначе считается 14400. Если `asOf`/`attemptAt` > `now + 60` → не свежая. Несогласованность: `asOf > attemptAt + 60`. Почему: буквальное «`nextAt` > now + 60 → не свежая» из T1 делает не свежей любую нормальную запись.
2. N9: кеш отвергнутых `raw_url` хранится на диске, в `sync-state.json` → `rejectedRaw` (16 hex от sha256 URL → время отказа). Срок 24 ч, ≤ 64 записи. Почему: на VPS каждый тик — новый процесс, кеш в памяти не работает. Сам URL не хранится (A1-25).
3. Задержка видимости gist (5 мин) — вне допуска «0 пар»: синтез §D опирается на согласованное чтение API gist. Ячейка симулятора остаётся skip с причиной.
4. «≤ 1 пары на 15 мин простоя» проверяется как «≤ 1 лишний запрос на 15 мин» (synth §D).
5. Порядок прохода A3-02 — по синтезу: GET → сохранение попытки → PATCH №1 → запрос → PATCH №2. Строка тест-плана исправлена.

## 2026-10-15 — REMOTE-LIMITS A3: поправки к §D по шагу 1 (решение Юрки)

1. Цепочка чужих дедлайнов: если между двумя принятыми чужими `retryUntil` своего опроса не было, `firstSeenAt` наследуется, и вся цепочка ограничена 24 ч. После срабатывания потолка помечается `until = firstSeenAt + 24 ч`; пометка снимается, когда `mine.last_attempt ≥ firstSeenAt + 24 ч`. Почему: иначе сосед, который каждый тик публикует `retryUntil = now + 23 ч`, подавлял бы опрос навсегда. Это нарушение И-инварианта «≥ 1 запрос за 24 ч» (A3-20(c)). Векторы для этого случая добавляются в общую фикстуру `decide-vectors.json` — для C4-04 (Swift).
2. Чужая запись без `lastSeenAt` или с испорченным `lastSeenAt` считается неживой: в подавлении и тай-брейке не участвует (безопасная сторона, П7).

## 2026-10-15 — REMOTE-LIMITS A3: обрыв цепочки чужих дедлайнов, A1-14 vs N8 (решение Юрки)

1. Цепочка чужих `retryUntil` наследует `firstSeenAt`, только если новый срок принят, пока прошлый `effective` ещё действует или истёк ≤ 900 с назад. Иначе — новая цепочка, `firstSeenAt = now`. Почему: если своего опроса не было несколько дней (подавлял свежий чужой снимок), настоящий 429 у соседа не должен из-за давнего `firstSeenAt` вести к немедленному опросу в действующее ограничение. Инвариант «≥ 1 запрос за 24 ч» сохраняется: при разрыве > 900 с срок истекает, и на ближайшем тике мы due.
2. Крайний случай «обычный срок кончился ровно на потолке, приходит новый чужой срок»: событие `remote_retry_capped` не пишется, опрос есть — принимается как есть.
3. A1-14 (`test_gist_body_over_16_mib`) противоречит N8 (A3-30) только заглушкой стенда: в тест добавляется маршрут листинга. Проверка предела тела (16 МиБ, чтение cap+1) остаётся.
4. Пометка потолка (`until = firstSeenAt + 24 ч`) — тоже «прошлый effective»: если она истекла > 900 с назад без своего опроса, новый чужой срок открывает новую цепочку.
