# 024 — Id секретного gist в памяти проекта, а память лежит в публичном репозитории

**Дата:** 2026-11-01 · **Веха:** C6 (T3 выпуска) · **Находка:** T3 B1 (blocker)

## Что случилось

12.10 (`657e076`) Юрка записал в `HEARTBEAT.md` («Операционное») рабочий id секретного gist синхронизации. Записывал для себя, чтобы помнить, какой gist наш. Репозиторий `claude-codex-limits` публичный, ветка `remote-limits` запушена не позже 18.10. Id секретного gist — это ссылка на чтение: снимки всех машин и вся история ревизий, включая старое имя владельца и hostname.

- Правило «id gist — ссылка доступа, не печатать» Юрка соблюдал в выводе команд (`grep -v '^Gist: '`), но не в своих файлах памяти.
- `tools/secrets-check.sh` 32-символьные hex-id не ловит: их не отличить от SHA и хэшей. Да и pre-commit-хука в репозитории проекта не было.
- Нашёл только T3 перед публичным выпуском, через 20 дней.

Последствия: id убран (`0322fff`), но в истории он навсегда. Gist пришлось пересоздавать (П4-б, решение владельца), подписи аккаунтов сброшены, метки сменились посреди замера G1–G4.

## Правило на будущее

1. **В файлы проекта (HEARTBEAT, decisions, отчёты, брифы) не пишем ни id, ни ссылки секретных ресурсов** — gist, приватных URL, инвайтов. Пишем описание: «gist синка (описание "… usage sync", 4 файла)». Найти его можно `gh gist list | grep -c` без вывода id.
2. **Публичен ли репозиторий проекта, проверяем один раз и пишем в шапку HEARTBEAT.** Если публичен, вся память проекта считается публикацией.
3. **В репозитории каждого проекта стоит pre-commit со сканером** (`sh tools/secrets-check.sh --install <repo>`). Здесь его не было.
4. **Сканер дополняется шаблоном контекста:** hex-id рядом со словами `gist` / `gists/` / `gist.github.com`. Это задача для тулинга штаба.
