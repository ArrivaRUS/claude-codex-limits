# 016 — Требование PRD без теста всплыло на боевой выкатке
**Дата:** 2026-10-18 · **Фаза:** REMOTE-LIMITS A5 (выкатка на VPS)

## Что сломалось
PRD P1/S4: «на headless VPS токен GitHub хранится только в файле 0600». Владелец выполнил `ccl-sync login` из терминала рабочего стола VPS (XFCE, разблокированный keyring), и код положил токен в Secret Service. Под systemd-таймером тот же keyring заблокирован — синхронизация встала сразу после первого ручного прохода. Ни один из ~750 тестов, ни 3 цикла ревью и T2 этого не поймали.

## Почему
S4 в тест-плане была сформулирована как свойство среды («на VPS нет secretstorage и сессии D-Bus»), а не как поведение кода. Предпосылка PRD (2026-10-12) была неверна: на VPS есть XFCE с keyring, и у CLI, запущенного из терминала рабочего стола, есть D-Bus. Тесты издателя подменяли Secret Service целиком и не проверяли, КУДА пишется токен при включённом издателе. Боевой прогон (P21½) был заменён инструкцией выкатки — первый реальный вход случился уже на A5.

## Как чиним
`0457333`: при `publisher: true` оба пути входа пишут токен только в файл, проход не читает его из Secret Service даже разблокированного, `status`/`publisher --enable`/`install.sh --publisher` подсказывают перелогиниться. Тесты A5-01…A5-11; трассировка S4 → тесты в test-plan.

## ПРАВИЛО НА БУДУЩЕЕ
- Каждое требование PRD вида «X хранится/живёт только в Y» — тест на поведение кода при ДОСТУПНОЙ альтернативе (Y-не-Y), а не допущение о среде. В трассировке тест-плана у каждого S/P-требования — ID теста; «свойство среды» не принимается как покрытие.
- Перед выкаткой сервиса, работающего под systemd/таймером, — боевой прогон входа и одного прохода В ОКРУЖЕНИИ ТАЙМЕРА (без `DBUS_SESSION_BUS_ADDRESS`/`DISPLAY`, `XDG_RUNTIME_DIR=/run/user/<uid>`), а не только из интерактивного шелла.

## Куда внесли правило
`docs/test-plan-remote-limits.md` (трассировка S4 → A5-01…A5-11); `docs/rollout-remote-limits-vps.md` — вход владельца в окружении таймера (после фикса — обычный вход, код сам выберет файл).
