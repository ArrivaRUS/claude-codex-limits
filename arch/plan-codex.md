**A. Контракт gist v1.1**

Оставить `schema: 1`, имя `machine-<id>.json`, прежние `machine`, `updated`, `tz`, `days`. Добавить один ключ `remoteLimits`. Число «1.1» — версия документа контракта; `remoteLimits.version: 1` — версия расширения.

Предлагаемая форма:

```json
{
  "schema": 1,
  "machine": {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "vps",
    "os": "Linux",
    "app": "linux NEW"
  },
  "updated": "2026-10-12T10:10:00Z",
  "tz": "Etc/UTC",
  "days": {
    "claude": {

        }
      }
    }
  },
  "remoteLimits": {
    "version": 1,
    "keyId": "0123456789abcdef",
    "lastSeenAt": "2026-10-12T10:10:00Z",
    "accounts": {
      "a1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": {
        "provider": "claude",
        "limits": {
          "plan": "max",
          "tier": "max_20x",

          "session": {
            "usedPct": 31.5,
            "resetAt": "2026-10-12T14:00:00Z"
          },
          "week": {
            "usedPct": 48,
            "resetAt": "2026-10-16T08:00:00Z"
          },
          "models": [],
          "resetCredits": null,
          "status": "ok",
          "statusAt": "2026-10-12T10:00:02Z",

              "input": 10, "output": 20, "cacheRead": 0,

    "unattributedDays": {},
    "labels": {}

```

Дополнительные точные формы:

- `models`: массив `{name: string, usedPct: number, resetAt: UTC|null}`, максимум 8.
- `labels[accountId]`: `{text: string|null, changedAt: UTC}`; `null` — сброс подписи к автоматической.
- `limits: null` — есть история аккаунта, но нет снимка лимитов.
- `asOf: null` допустим до первого успеха; тогда окна отсутствуют/`null`, `models: []`, `resetCredits: null`.
- `lastAttemptAt: null` — запросов ещё не было. `statusAt` меняется и при локальном обнаружении истёкшего входа, без фиктивного изменения `lastAttemptAt`.
- `unattributedDays` имеет прежнюю форму `days`: продукт → дата → модель → шесть счётчиков.

Границы расширения:

| Поле | Проверка |
|---|---|
| `provider` | Только `claude` / `codex` |
| ID аккаунта | `a1:` + 64 строчных hex-символа |
| `keyId` | 16 строчных hex-символов |
| Проценты | Конечное число 0…100; bool запрещён |
| `resetCredits` | Целое 0…1 000 000, bool запрещён |
| `mode`, `intervalSec` | `auto` / `fixed`; 900/1800/3600/14400 |
| Статус | Перечень C2; неизвестный преобразуется в `error` |
| Время | ISO-8601 UTC с `Z`, дробные секунды допустимы |
| Строки | Подпись ≤32 Unicode-символов; модель/plan/tier ≤64; без управляющих символов |
| Коллекции | ≤32 аккаунтов на файл; ≤45 дат; ≤256 моделей на дату |
| Размер | Метаданные лимитов ≤4 KiB/аккаунт; расширение ≤8 MiB |

Невалидное окно отбрасывается отдельно. Структурно битый `limits` отбрасывается целиком, **его `days` сохраняются**. Невалидное расширение не отменяет чтение корневого `days`. Дубликаты JSON-ключей в расширении отклоняются.

**Совместимость доказуема непосредственно по обоим merge:**

- Python проверяет `schema == 1`, машину и дату, затем перебирает исключительно `obj["days"]`; неизвестные соседние ключи не используются: [sync.py:355](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/sync.py:355).
- Swift делает те же проверки и затем читает исключительно `obj["days"]`: [LimitsMonitor.swift:2740](/home/yurka/VibeCoding2/2026_06_UsageLimits/Sources/LimitsMonitor.swift:2740).

Следовательно, одинаковый корневой `days` даёт старому читателю одинаковые суммы с расширением и без него. Это нужно закрепить общей фикстурой и прогоном **старых** merge, а не только новых парсеров.

Правила записи и суммирования:

1. Корневой `days` — проекция суммы `accounts[*].days` по провайдеру плюс `unattributedDays`.
2. Новый читатель использует разбиение по аккаунтам **вместо** корневых сумм. Складывать оба представления запрещено.
3. Проверять равенство проекции корневому `days` по продукту. При нарушении использовать корневой расход этого продукта как неатрибутированный; лимиты валидировать независимо.
4. Публиковать только собственные наблюдения и собственный расход. Полученный из gist снимок не перепубликовывать от имени своей машины.
5. Хешировать расход, лимиты, статусы, расписание и правки подписей. Сейчас Python и Swift хешируют только расход: [sync.py:333](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/sync.py:333), [LimitsMonitor.swift:2533](/home/yurka/VibeCoding2/2026_06_UsageLimits/Sources/LimitsMonitor.swift:2533).
6. Подписи объединять по `(changedAt, machine.id)`; собственные правки читателя могут существовать без локального аккаунта.
7. Старые аккаунты удалять из актуального набора по их собственному последнему наблюдению/расходу, а не по регулярно обновляемому времени машины.

**Коллизия C6/V5:** без изменения расхода и при Auto 4 ч файл законно молчит несколько часов. Поэтому возраст `updated >30 мин` сейчас не доказывает отключение машины. Предлагаю `lastSeenAt` и heartbeat раз в 10 минут, включённый в хеш. Это требует явно добавить heartbeat в разрешённые причины записи C6. `asOf` и `nextAttemptAt` ради heartbeat не передвигать.

Допущение «+4 KiB на аккаунт» применимо к лимитам, **не ко всему расширению**: дублирование 45-дневного расхода увеличивает размер пропорционально числу моделей и дней. Это сознательная цена простого, проверяемого переходного контракта.

**B. Метка аккаунта**

| Провайдер / платформа | Источник |
|---|---|
| Claude / Linux | Токен из `.credentials.json`; стабильный `account.uuid` из бюджетного `/api/oauth/profile`, затем локальный кеш привязки |
| Claude / macOS | Токен через существующий тихий Keychain-read; тот же resolver профиля и кеш |
| Codex / обе | `tokens.account_id`; сверка с `tokens.id_token` → `https://api.openai.com/auth.chatgpt_account_id` |
| Нет достоверной идентичности | Неатрибутированный расход; никаких догадок по плану, имени машины или токену |

Для Codex использовать идентификатор выбранного аккаунта/workspace, которому соответствует `chatgpt-account-id` запроса лимитов. Email не нужен. Такое разделение полей подтверждается [исходником Codex](https://github.com/openai/codex/blob/main/codex-rs/login/src/token_data.rs); проект уже использует `tokens.account_id` в обоих портах: [limits.py:496](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/limits.py:496), [LimitsMonitor.swift:502](/home/yurka/VibeCoding2/2026_06_UsageLimits/Sources/LimitsMonitor.swift:502). Несовпадение двух источников — ошибка идентичности, не выбор «предпочтительного» значения.

Формула одинакова в Python/Swift:

```text
canonical = JSON-массив [provider, identityKind, canonicalProviderId]
            в заранее фиксированном компактном UTF-8 представлении
accountId = "a1:" + hex(HMAC-SHA256(K, "ccl-account-v1\0" || canonical))
keyId     = первые 16 hex(HMAC-SHA256(K, "ccl-key-id-v1"))
```

UUID нормализуется к нижнему регистру; остальные ID считаются непрозрачными строками. Опубликованный ID не зависит от срока или перевыпуска токена.

**Общий ключ:** случайные 32 байта, создаются один раз для набора. Linux: `CONFIG_DIR/account-key`, macOS: `~/.claude-limits-monitor/account-key`; файл 0600, каталог 0700, атомарная запись, запрет symlink. Выбор файла на macOS избавляет эту фичу от нового фонового Keychain-доступа.

Ключ переносится владельцем через защищённый канал, например SSH/SFTP, с импортом из файла/stdin; не через gist, argv, окружение или чат. В gist хранится только `keyId`. Новая машина не генерирует независимый ключ автоматически, если набор уже существует. Ротация GitHub-токена ключ не меняет.

Без ключа машина может **читать** опубликованные аккаунты: для этого HMAC вычислять не требуется. Собственный расход остаётся неатрибутированным; статус объясняет необходимость импорта ключа. Несовпадение `keyId` обнаруживается до публикации собственных именованных аккаунтов.

**Claude требует осторожной привязки к текущему входу.** Нельзя предполагать, что `oauth/usage` содержит стабильный ID: текущий парсер такого источника не устанавливает. Профиль — отдельный тип бюджетной попытки, максимум раз за 24 часа, вместо очередного обращения, без немедленного запроса usage следом.

`~/.claude.json.oauthAccount.accountUuid` можно рассматривать как дополнительный локальный источник, но не как безусловное доказательство принадлежности текущего токена. В официальном репозитории есть первичный отчёт о рассогласовании этого кеша и действующего токена после смены аккаунта: [Claude Code #81231](https://github.com/anthropics/claude-code/issues/81231).

Кеш профиля связывать с поколением прочитанных credentials; локальный HMAC-отпечаток поколения допустим, **в gist и журнал он не попадает**. При смене непрозрачного токена без достоверной связи с аккаунтом — `identity_unknown`, не перенос старой метки. Если суточный бюджет профиля исчерпан, ждать: иначе A6 нельзя гарантировать.

Это реальная граница требований: при частой ротации непрозрачных Claude-токенов отсутствие связанного локального ID может ухудшить свежесть. До реализации нужен обезличенный контрактный fixture профиля и доступных локальных identity-полей; реальные credentials для теста не нужны.

**D. Координация B2**

Минимальное дополнительное условие допуска:

```text
scheduled:
    локальное расписание наступило
    AND прошло ≥900 с после всех известных попыток аккаунта
    AND отсутствует успешный remote sample моложе текущего интервала
    AND истёк max(локальный retryUntil, retryUntil всех источников)

manual:
    те же пол 900 с и общий Retry-After
    без ожидания обычного Auto-интервала
```

Использовать **`lastAttemptAt`, а не только `asOf`**: неудачный запрос тоже расходует бюджет. Идентификационный запрос также входит в общий журнал обращений. Отдельный бюджетный gate позволяет учитывать profile, не выдавая его за успешное наблюдение процентов.

Удалённые данные **не передавать в `PollState.observe()`**: этот метод меняет `last_attempt` и интервал, что превратит пропуск B2 в другую семантику Auto. Удалённое показание обновляет карточку и условия пропуска, но не изображает локальный запрос. Основание: [polling.py:53](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/polling.py:53).

**Числовой допуск простого механизма:**

- Публикация и чтение каждые 600 с дают до **1200 с невидимости** новой попытки.
- С проверкой исполнителя каждые 300 с получается до **1500 с, то есть 25 минут**, до применения информации.
- За такое окно каждая из `N` машин с полом 900 с может выполнить до двух запросов.
- Верхняя оценка: **2N запросов; до 2(N−1) дополнительных** относительно одной машины. Для двух машин — **до двух дополнительных запросов за 25 минут**, минимальный промежуток между машинами может быть практически нулевым.
- Оценка условна: исправный GitHub, ограниченные задержки доставки и согласованные часы. При сетевом разрыве конечной границы времени сходимости нет.

Причём это не обязательно только стартовая гонка: A запросила в 10:15, её новый снимок ещё не опубликован, B в 10:16 видит старый `asOf=10:00` и тоже запрашивает. Фазовое расхождение может повторяться.

**Поэтому этот допуск нельзя объявить выполнением G1 или принятого B8.** Допущение PRD «gist недоступен — все опрашивают самостоятельно, и G1 сохраняется» отвергаю. Свежий GET перед ручным запросом тоже не устраняет гонку двух одновременных GET.

Для строгого варианта рекомендую **единственного активного владельца опроса аккаунта и передачу права только после подтверждённого прекращения старого владельца**. Это дополнительный admission-gate; Auto остаётся прежним. При разделении сети владелец продолжает работу, остальные ждут; автоматическое захватывание права по истечению lease исключить. Допуск такого перехода — **0 дополнительных запросов**, ценой задержки ручного действия/переключения источника.

Это отдельное решение для среза B: нужно определить управление правом и его передачу; маскировать его «свежестью снимка» нельзя.

**B6:** дедлайны объединять максимумом и сохранять локально до истечения, даже если соответствующий файл исчез из следующего GET. Последующий `ok` другой машины не сокращает ещё действующее ограничение. Дедлайн >24 ч сохраняется полностью и показывается в status; не обрезается до суток.

Не использовать GitHub-backoff для лимитов: [sync.py:495](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/sync.py:495) ограничивает его часом. Provider-parser уже не имеет такого cap: [quota_refresh.py:112](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/quota_refresh.py:112). Распространение неизвестного другим машинам Retry-After имеет ту же сетевую границу, что B2.

**E. Политика токенов S1**

`read_only` — явная политика источника credentials, не результат поиска процессов CLI. Отсутствие процесса сейчас не означает, что CLI не запустится через секунду. Для совместно используемых стандартных файлов на VPS и macOS Codex — значение по умолчанию.

| Состояние | Действие издателя | Публикация |
|---|---|---|
| Опрос выключен | Не читает credentials, Keychain и журналы | Локального снимка нет |
| Вход отсутствует | Запросов 0 | `signed_out`, если аккаунт достоверно известен |
| Файл битый/недоступен | Запросов 0; повтор локального чтения следующим тиком | Неизвестная идентичность / `error` |
| Токен пригоден | Usage только после admission | Успех обновляет значения и `asOf` |
| Access истёк/слишком близок к expiry | Никакого refresh и usage | `expired`, прежние значения и `asOf` |
| 401 | Не повторять и не refresh | `expired` |
| 429 | Backoff и общий дедлайн | `rate_limited`, прежний снимок |
| 403/5xx/сеть | Классификация ошибки без вывода «вход истёк» | `error`, прежний снимок |
| CLI заменил credentials | Перечитать, проверить идентичность и admission | Возобновление после успешного запроса |

Для Claude сохранить запас 120 с, Codex — 60 с. Неизвестный срок действия — отдельная ошибка credentials, а не разрешение обновить OAuth.

**Критическая стыковка:** `read_only` проверяется **до** replay `_PENDING`, поскольку replay сам записывает файл: [limits.py:187](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/limits.py:187), [limits.py:497](/home/yurka/VibeCoding2/2026_06_UsageLimits/linux/ccl/limits.py:497). В `read_only`:

- `deadRefresh`/`deadCodexRefresh` не очищаются и не превращаются в разрешение refresh.

- Горячее переключение при незавершённой ротации запрещено: уже выданную новую пару нельзя молча потерять. До переключения требуется завершённая legacy-операция либо подтверждённая новая пара от CLI; неопределённость отображается как ошибка, без новой ротации.

**H. Риски, альтернативы, вопросы**

1. **B2 — блокирующий вопрос до реализации координации.** Простой fresh-skip имеет указанный допуск до двух дополнительных запросов для двух машин за 25 минут; он несовместим с гарантией нулевых нарушений G1. 4. **Claude после ротации:** если доступен только непрозрачный токен и старый несвязанный profile-cache, одновременно гарантировать немедленную атрибуцию и profile ≤1/сутки невозможно. Без доказательства принадлежности выбирать неизвестную идентичность.
