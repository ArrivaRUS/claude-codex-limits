## Ответы по местам, где Codex решал сам

**(а) `ContextVar` для бюджета чтения — корректно.** `_raw` ставит значение и всегда сбрасывает в `finally` токеном
(`sync.py:112-121`); проба: после вызова `_raw_cap.get() is None`. Значение читается только в `_transport` и только для
неавторизованного GET (`sync.py:57-62`) — запросы API с токеном и POST Device Flow его не видят. Потоки изолированы
(каждый поток — свой контекст; проба на трёх потоках с разными cap — каждый получил свой). Вложенных `_raw` нет;
даже если бы были, `set/reset` по токену корректно восстанавливает внешнее значение. Если подставной `transport`
унесёт запрос в другой поток, cap до `common.http` не дойдёт, но `_bounded_response(response, cap)` всё равно
отбросит тело больше остатка — предел соблюдён, перерасход чтения ≤ 8 МиБ. Неявный канал — цена сохранения
пятиаргументного шва; приемлемо, комментарий есть.

**(б) Отказ `raw_url` не с `gist.githubusercontent.com` до запроса — v1 не ломает.** `raw_url` берётся только из ответа
`GET /gists/{id}` (`sync.py:799-801`), а API жёстко `https://api.github.com` (`sync.py:30`, `_api_origin`) — GitHub
Enterprise не поддерживается вообще, другого raw-хоста у github.com нет. Писатель gist `raw_url` не контролирует.
Прочие вызовы `_raw` отсутствуют. Регистр хоста: GitHub отдаёт строчными, `GIST.githubusercontent.com` будет отвергнут —
допустимо. Остаётся только видимость отказа (r2-m2) и протокол (r2-m1).

**(в) `_GistRawRedirect` — корректен.** Вызов `self.parent.open(new, timeout=req.timeout)` — тот же приём, что у штатного
`http_error_302`; заменена только `redirect_request` (которая дренирует `fp.read()`). Счётчик на экземпляре обработчика,
а обработчик создаётся заново на каждый `common.http` → бюджет переходов на запрос, не на процесс: 3 перехода → 200,
4-й → `RAW_REDIRECT_REFUSED` (проверено настоящим urllib). Промежуточный `fp` закрывается до разбора `Location`; итоговый
ответ закрывает `with` в `http()`; HTTPError с последнего хопа читается с `max_body`. Таймаут 30 с на сокетную операцию
каждого хопа (до 4 соединений); общего дедлайна нет — это N3-хвост в A3. Утечки заголовков нет: на `_raw` нет
`Authorization` (`sync.py:114`), а цель всегда тот же хост `gist.githubusercontent.com` по https; копирование
unredirected-заголовков — nit n3. Методы кроме GET/HEAD и `Location` с управляющими символами — отказ.

**(г) Нормализация `accountByDay` — гонок и лишних записей нет.** `refresh` грузит индекс без нормализации под
`file_lock("usage-index")`, `scan` нормализует и возвращает `changed` только при реальном отличии (`old != clean`) —
запись на диск один раз после апгрейда (нет ключа) или после повреждения, дальше `prune` видит уже чистое и `False`.
Ветка «замок занят» нормализует только в памяти и не пишет. `load_index()` в CLI/GUI — только чтение в памяти.
Изменение значений словаря при итерации в `prune` (`usage.py:124-128`) безопасно — набор ключей не меняется.

## Открытые вопросы разработчика — рекомендации

**(1) Второй рубеж N1 (перехват сбоя записи `sync-remote.json`) — в A3, не сейчас.** Первый рубеж полный: все строки,
попадающие в `remote`, прошли `_text` или собраны из чисел (fuzz 3000 итераций — 0 сбоев кодирования). Перехват на уровне
`write_json` не знает, какой файл виноват, и превратит баг валидатора в тихую потерю кэша. Правильное место — A3,
где `run_pass` и так «ловит всё и пишет класс события» (П6-а). Если нужен дешёвый рубеж раньше — не `try` вокруг
записи, а проверка кодируемости на машину внутри `merge` (`json.dumps(machine, ensure_ascii=False).encode()` → пропуск
машины), 3–4 строки; это допустимо и в этом цикле, но не обязательно.

**(2) Видимость отказа редиректа / чужого `raw_url` — да, единообразно, по R1.** Машина, исчезнувшая из списка без
единого сигнала, хуже, чем ошибка: владелец не отличит «машина не синхронизируется» от «транспорт отказал». Сделать как
у большого файла: файл пропущен, `lastOkAt` двигается, `res.ok=False`, `lastError` «raw_url отклонён (редирект/хост)».
Враждебный писатель этим не управляет (`raw_url` и ответы — от GitHub), так что шума не будет; если сработает — это
сигнал MITM/прокси или изменения GitHub, который владелец должен видеть. Цена — 3 строки + тест в A1-18. Рекомендую
в этом же цикле вместе с r2-m1 (одно место в протоколе), допустимо — в A3.

## Security

Чисто в пределах скоупа: фиксы закрывают DoS одним файлом (суррогаты), вывод ESC в терминал, обход предела через
редирект, перебор бюджета. Новых каналов утечки нет: `Authorization` на raw не уходит, переход только на тот же хост
по https; `localId` по форме; ПДн в блок не попадают.

**Security surface: да** — парсинг недоверенного входа (чужие файлы gist), сетевые пределы и политика редиректов,
чтение локальных файлов входа (`localId`). → T2: повторный проход `security-analyst` по фиксам (N1–N6, N12) до мержа.

**Вердикт:** APPROVE с правками — r2-m1…r2-m4 (все minor, каждая — несколько строк + вектор теста) желательно в этом же
цикле; nit — по желанию. Ревью 3 не требуется, если правки ограничатся этим списком: достаточно зелёного набора и
сверки дифа Юркой.
