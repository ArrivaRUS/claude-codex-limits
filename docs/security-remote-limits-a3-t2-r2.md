## 3. Находки

### N1 · major · обрыв прохода во время переоткрытия теряет счётчик, и опроса нет никогда
- **Где.** `publisher.py:327–329`: при `stale`/`busy` сначала идёт `_rollback(..., old_saved, ...)`, потом `_locked(reopened=True)`. Счётчик `_publishFailures` и проверка «`now − last_attempt ≥ max(I, 24 ч)`» срабатывают только после неудачи **переоткрытой** сессии (`:331–336`).
- **Вектор.** Издатель на VPS убит посреди переоткрытия: `RuntimeMaxSec`/`TimeoutStartSec` юнита A4, OOM, ручной `kill`. Откат уже вернул старое состояние, счётчик не вырос. Следующий тик повторяет то же самое — это S2 в чистом виде, без следов в `status`.
- **Почему это реально.** Проход длинный:
  - Проба P5e (5 raw × 25 с + merge 60 с, без ожидания замков): 270 с виртуальных на тик.
  - Худший случай по коду: `quota` 30 с, затем дважды [чтение 60 с + один таймаут до 30 с + merge + `sync` 60 с + PATCH 20 с], затем провайдер и PATCH №2. Итого ≈ 10 мин.
  - Sol добавил: фаза заголовков не ограничена сроком. Повторные `100 Continue` дают 23 с при timeout 2. Я воспроизвёл: 8 с при timeout 2. Значит, «худший проход» не строго конечен, и одним `RuntimeMaxSec` N1 не закрыть.
- **Воспроизведение (P5f).** Merge по 130 с, `Kill` (BaseException) на втором `open_cycle` в тике. Результат за 2 суток: 0 запросов, `_publishFailures` на диске нет, `pass_failed` = 0. Sol воспроизвёл независимо: 577 тиков, 0 запросов.
- **Фикс:**
  - (а) Неудачу текущего тика учитывать и проверку 24 ч делать **до** переоткрытия. Счётчик +1 и решение о fallback входят в цель отката, которая журналируется в `_rollback`. Успешное переоткрытие сбрасывает счётчик в 0. Тогда обрыв в любой точке не мешает 3-му тику.
  - (б) В A4 не ставить `RuntimeMaxSec` ≈ 300 с. Лимит должен быть не меньше худшего прохода, ≥ 15 мин. Это вместо моего S6.
- **Тест.** A3-43, см. §5.

### N2 · minor · `timeout` стал общим сроком для всех вызовов `common.http()`, включая ротацию токенов
- **Где.** `common.py:929`: `deadline = monotonic() + timeout`. Срок проверяется перед каждым чтением тела (`:863–891`), в том числе когда тело уже в буфере.
- **Кого затрагивает:**
  - POST `/oauth/token` Anthropic и OpenAI (`limits.py:367`, `:789`, срок 15 с; только `guarded`, то есть не на издателе);
  - refresh GitHub (`sync.py:211` → `transport`, 15 с) — **на всех машинах, включая VPS-издатель**;
  - updater (`update.py:215`, `:238`, 120 с на ≤ 32/64 МиБ) — это R2-m1 у ревьюера.
- **Проба.** Заголовки 200 приходят на 1,85 с, тело — через 0,3 с, timeout 2 → `Resp(0, HTTP_DEADLINE, original_status=200)`, потеря 5 из 5. Раньше, когда срок считался на каждую операцию, ответ прошёл бы. Ответ, пришедший целиком до срока, проходит (12 из 12).
- **Последствие.** Одноразовый refresh-токен потрачен, а новая пара потеряна. Пользователь входит заново; на VPS это вход GitHub. Секреты не утекают.
- **Остальное в норме:**
  - предел `cap+1` не обходится: HEAD, 204, 1xx, HTTP/1.0 до EOF, chunked, `HTTPError.fp` — данные Sol и ревьюера;
  - медленная передача тела и поток trailer-строк обрываются по сроку (≈ 2,1 с при timeout 2);
  - 20 обрывов по сроку: fd 5 → 5, сервер видит закрытие;
  - 400 с медленным телом → status 400, `data None`, `deadRefresh` не ставится;
  - `_NoRedirect` и `_GistRawRedirect` не изменились: только `gist.githubusercontent.com`, ≤ 3 прыжков, без `Authorization`/`Cookie`.
- **Фикс.** Общий срок включать только явно, параметром `deadline=`, для чтений sync (gist, raw, листинг). Токен-эндпоинты и updater оставить с прежней семантикой. Это тот же фикс, что R2-m1.

### N3 · minor · испорченный маркер `_rollback` даёт вечный `pass_failed` (= R2-m2)
- **Где.** `publisher.py:206`.
- **Проба.** При `{"_rollback": {}}`: `KeyError` на каждом проходе, 289 `pass_failed` за сутки, 0 запросов, маркер остаётся. При `saved` = 5 или `[]`: один `AttributeError`, дальше проход восстанавливается сам.
- **Оценка.** Из gist маркер не приходит: нужна порча локального файла 0600 тем же UID или смена версии формата. Это отказ опроса, утечки нет.
- **Фикс.** Как в R2-m2: при неверной форме снять маркер, сохранить консервативную попытку, записать событие O1.

### N4 · minor, существовало до фикса · откат объявленной попытки после успешного PATCH (Sol)
- **Где.** `sync.py:910`: `st.update(...)` после 2xx бросает `OSError` → `write()` возвращает `False` с `write_error="storage"` (`:875`) → издатель откатывает попытку, которая уже лежит в gist.
- **Последствие.** Соседи ждут ≤ 960 с (`remote_attempt`), а мы не опрашиваем. Это фантомная попытка в пределах уже принятого П7. Счётчик N1 через 3 тика ведёт к опросу.
- **Фикс.** Отделить «сеть подтвердила PATCH» от «не записался локальный отпечаток»: в этом случае не откатывать.

### Info
- SIGKILL между `mkstemp` и `replace` может оставить временный файл 0600 в каталоге состояния. Это существующее поведение `write_atomic`, секретов в нём нет.
- `claude_token_policy_blocks` не учитывает пустой `accessToken` и отсутствующий `expiresAt` (R2-n1). Запросов это не добавляет: `fetch_claude` при `never` выходит без HTTP.

1. **`common.http()`.** Обхода пределов тела, утечки сокетов и изменения редиректов нет. Зависание по фазе заголовков (1xx) было и раньше, сервер в этом случае доверенный по TLS. Новое — N2.
