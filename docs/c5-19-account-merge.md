## Диагноз со строками кода

Ключ карточки — продукт + label. Label своего показания вычисляется через HMAC
от идентичности **этого показания**: `Sources/RemoteLimits.swift:222`, `:686`,
`:688`. Подпись аккаунта на склейку не влияет. Чужие accounts файлов машин
читает `mergeV11` (`:573`), привязывает к машине (`:632`), складывает в
`remote.accounts` (`:662`, `:669`). `resolveAccounts` группирует их по label
внутри продукта (`:693`, `:699`). Боевой путь: `captureAccountFrame`
(`Sources/LimitsMonitor.swift:4872`) → `remoteAccountFrame`
(`Sources/RemoteLimits.swift:1046`) → `resolveAccounts` → `simpleCardViews`
(`Sources/LimitsMonitor.swift:4923`) → Simple draw.

Разводящее условие — `Sources/RemoteLimits.swift:779`: при локальных данных
карточка создаётся **даже при localLabel == nil**, с пустым массивом источников.
Следующий цикл (`:782`) исключает чужую карточку только при
`hasLocal && label == localLabel`. Непустая чужая label не равна nil: получаются
две карточки и два Codex в шапке. Равные labels в gist этого не исправляют:
свой файл намеренно исключается из чужих accounts.

Почему nil после старта: **до патча**, `9f00e74:Sources/LimitsMonitor.swift:8534`
и `:8535` читали значения через `dict2ld` (`:790`), который не читает accountId,
затем `render(c, x)` (`:8538`) вызывался без readingIds/sampleProducts.
`ReaderLocalSnapshot.ids` изначально пуст и обновляется только для
identityProducts. При этом писатель **уже сохраняет** accountId рядом с
процентами (`Sources/RemoteLimitsC4.swift:588`). Свежий запрос возвращает ID
через `Sources/LimitsMonitor.swift:8889`, `:8890`; до него модель разделена.
Это доказанный путь воспроизведения модели; cache.json владельца не читался.
Старый кэш без accountId безопасно связать с аккаунтом нельзя.

## Исправление и значения

`ReaderLocalSnapshot.restore(cache:)` (`Sources/LimitsMonitor.swift:3522`)
восстанавливает данные и сохранённый рядом accountId одним модельным шагом.
ID проверяется как 8…64 `[0-9a-z-]`; без корректного ID, времени или показаний
привязка не создаётся. Текущий CLI-вход не читается и не приписывается старым
значениям. Запуск вызывает этот метод (`:8551`), затем обычный render без записи
новой истории/сигналов/запроса к провайдеру.

С восстановленным ID существующий резолвер даёт одну карточку, `macbook, vps`
и отдельные sourceReadings. **PRD V3** (`docs/prd-remote-limits.md:167`) прямо
задаёт наибольший успешный asOf, при равенстве своё
(`Sources/RemoteLimits.swift:724`). Для фикстуры это 57%, ↻1, нет сессии;
точки рыжая и зелёная по UX §3 от31.10. Временного правила и открытого вопроса
к спеке нет. Шапка использует общий `remoteSimplePanelSubtitle`
(`Sources/RemoteLimitsC3B.swift:3`, вызов `Sources/LimitsMonitor.swift:5249`);
дубль исчезает благодаря единственной карточке аккаунта.

## Второй симптом: свой Codex не обновляется

Это допускается дизайном, **не доказанный дефект опроса**. PRD B2 запрещает
собственный опрос при свежем чужом показании того же аккаунта. Чужая попытка
моложе960с → `remote_attempt` (`Sources/RemoteLimitsC4.swift:83`), успешный
чужой asOf моложе своего интервала+60с → `fresh_remote` (`:86`). При VPS
каждые900с и локальном интервале1800с условия могут постоянно откладывать свой
запрос. `readAndDecide` завершает тик без fetch/apply (`:370`, `:379`), поэтому
свои asOf/attemptAt остаются прежними, включая перезапуск. `publisherInput`
в `Sources/LimitsMonitor.swift` публикует свой сохранённый снимок, не заменяя
его чужим asOf. Для объяснения не требуется растягивание Auto.
Причины каждого тика19:34…22:09 без poll_skipped не установлены; пользовательские
журналы не читались. Алгоритм опроса не изменён.
