## 2. Находки

### S1 · major · будущий `lastSeenAt` делает испорченный статичный файл вечно «живым»
- **Где.** `coordination.py:49–51` проверяет только нижнюю границу: `seen < now − 1800`. После потолка и одного своего опроса цепочка открывается заново (`:89–91`, `:100–109`).
- **Вектор.** Один раз записанный файл с `lastSeenAt` и `retryUntil` = +10 лет. Это может быть писатель с токеном, который ушёл, или испорченный файл.
- **Проба P1.** I = 1800 с, тики по 300 с, 3 суток. Опросы раз в **24,5 ч навсегда**: интервалы 24,5 / 24,5 ч, три события `remote_retry_capped`. Контроль, тот же файл с `lastSeenAt = now`: одно ожидание 24 ч, дальше опрос каждые 0,5 ч. Интервал между опросами равен 24 ч + I, то есть больше `max(I, 24 ч)`.
- **Что нарушено.** Решение Юрки 2026-10-15 №2: запись с испорченным `lastSeenAt` должна считаться неживой. Плюс A3-20(c). Sol воспроизвёл на 24 / 48,5 / 73 ч.
- **Фикс.** В той же строке добавить `seen > now + SKEW` → `continue`. Тот же вектор нужен в `decide-vectors.json`, по нему проверяется и Swift C4-04.
- **Тест.** Статичный файл (`lastSeenAt` +10 лет, `retryUntil` +10 лет), 3 суток → первый опрос в `NOW + 24 ч`, дальше интервалы ≤ I. Отдельно fuzz A3-20(c) расширить будущим `lastSeenAt`: сейчас симулятор этот случай не ловит.

### S2 · major · фаза чтения дольше 120 с даёт `publish_failed` на каждом тике и ни одного запроса
- **Где.** `fetched_at` и `fetched_mono` ставятся сразу после `GET /gists/{id}` (`sync.py:957–958`). Это происходит до чтения до 64 raw-файлов (таймаут 30 с на каждый), до листинга N8 (до 30 страниц × 20 с) и до merge. `_write_locked` отказывает при возрасте сессии больше 120 с (`:827–828`). Издатель откатывает попытку и выходит без запроса (`publisher.py:284–292`). На следующем тике всё повторяется.
- **Проба P5.** Один raw-ответ на 130 с → за 2 суток **577 `publish_failed`, 0 запросов**. У Sol 5 raw × 25 с, все ответы успешны → 0 PATCH и 0 опросов. Значит, хватает медленной сети, без враждебного содержимого.
- **Замер.** Merge 57 МиБ враждебных root-`days` занимает 34–43 с CPU, на слабом VPS дольше. Пиковая память пробы вместе с генерацией фикстуры — ≈ 0,6 ГиБ.
- **Отказ тихий.** `error=None`, CLI выходит с кодом 0 и печатает «Проход издателя завершён» (`cli.py:237`, находка Sol). `lastError` не пишется.
- **Что нарушено.** «Чужие файлы только откладывают опрос, ≥ 1 запрос за `max(I, 24 ч)`»: И1 и A3-20(c), синтез §C «следующий тик повторит». Для A5 это главное: издатель на VPS молча перестаёт опрашивать.
- **Фикс, нужны все три части:**
  - (а) общий дедлайн фазы чтения не больше 60 с. Остаток файлов пропускается, сессия считается частичной (`partial`);
  - (б) если PATCH №1 отклонён из-за старой сессии или занятого замка, один раз переоткрыть сессию. Если `publish_failed` идёт подряд ≥ 3 тиков или `now − last_attempt ≥ max(I, 24 ч)`, действовать как при недоступном gist (P6): запрос по своему расписанию, блок уходит следующим удачным PATCH. Остаточный риск — ≤ 1 пары на событие, это уже принято в П7;
  - (в) `publish_failed` должен быть виден: поле `result.error` или отдельный класс, `lastError`, ненулевой код выхода `--now`.
- **Тест.** Raw-ответы сдвигают часы на 25 с × 5. За `max(I, 24 ч)` должен быть ≥ 1 запрос провайдера, ошибка видна в `status` и в коде выхода.

### S3 · major (строже, чем m4 у ревьюера) · журнал O1 без предела размера, `clock_skew` на каждый ответ
- **Ротация.** `common.py:345–358` срабатывает при размере больше 1 МиБ, но отбрасывает только строки старше 45 дней. При обычном ходе журнал перерастает 1 МиБ примерно к 15–17-му дню (m4). После этого **каждая** запись перечитывает и переписывает весь файл с fsync.
- **Проба P3.** 3 МиБ свежих строк → **394 мс на одну запись**, размер не уменьшается.
- **`clock_skew`.** `sync.py:132–134` пишет `sync-state.json` и событие O1 на **каждый** ответ GitHub и raw при |skew| > 60 с. Проба P2: skew 120 с и 10 raw-файлов → 13 событий и 13 записей state за проход.
- **Сцепка с S2.** Сдвиг часов VPS больше 60 с (обычное дело для VPS, A3-20(e)) и много raw-файлов (враждебный писатель или режим N8) дают десятки событий за проход. Журнал растёт примерно на МБ в сутки, каждая запись стоит секунды. Проход минутами держит `quota`, а запись событий идёт внутри фазы чтения. Это прямо ведёт к S2.
- **Фикс:**
  - ротацию сжимать до целевого размера — последние ≤ 512 КиБ, независимо от возраста строк, под тем же замком;
  - `clock_skew` писать не чаще раза за проход или только при изменении больше 60 с относительно последнего записанного;
  - `clockSkew` в state сохранять раз за проход.
- **Тест.** Журнал 3 МиБ свежих строк, одна запись → файл < 1 МиБ, права 0600. Skew 120 с и 10 raw → ≤ 1 `clock_skew` за проход.

## 4. M1 и m3 из код-ревью с точки зрения И1–И4
- **M1** (`publisher.py:141` × `coordination.py:57–60`; `nextAt = max(..., retryUntil)` → сосед отбрасывает всю запись). И1 сохраняется: сосед опрашивает не чаще своего Auto. Цена — защита общего бюджета (A-2) пропадает ровно при 429: сосед сам упирается в ограничение и получает свой дедлайн. Для ИБ это minor; фикс ревьюера («`nextAt` = только своя частота») поддерживаю, новых векторов он не открывает.
