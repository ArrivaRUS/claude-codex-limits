# PRD — REMOTE-LIMITS: набор аккаунтов на всех компьютерах

Обновлено: 2026-10-12. Тип: internal, утилита владельца (macOS-приложение, Linux-трей, headless `ccl-sync`). Статус: принят G1 2026-10-12 с поправками. Автор: product-manager. База: macOS 3.2.7, Linux 0.4.5, контракт синка v1 (`docs/sync-protocol.md`). Риск-теги из интейка: `контракт`, `арх-граница`, `права`, `данные`, `ОС/сеть`, `необратимо`.

> Рамка (уточнение владельца 2026-10-12). Раньше схема была «все аккаунты на всех компьютерах», теперь — «набор аккаунтов на всех компьютерах». Аккаунты принадлежат владельцу и разложены по машинам. Каждая машина показывает статистику по **всем аккаунтам набора**, даже если какого-то из них на ней нет. Основная сущность — **аккаунт** (Claude-аккаунт, Codex-аккаунт), а не «продукт на этой машине».

Нумерация: правила `A` (аккаунт), `C` (контракт gist), `B` (бюджет опроса), `S` (безопасность), `P` (издатели), `V` (вид), `U` (расход и деньги), `N` (настройки), `O` (наблюдаемость). Истории — `RL-n`. Пометка **[доп.]** означает допущение PM, его подтверждает или отвергает архитектура либо владелец.

---

## 1. Фон и цели

### Почему сейчас
Команда агентов владельца работает на VPS (Ubuntu 26.04, headless для этой задачи, Linger включён). Там подписка **Claude Max 20x** (вход Claude Code: `~/.claude/.credentials.json`) и вход **Codex** (`~/.codex/auth.json`, `auth_mode chatgpt`). На MacBook установлено приложение проекта, но подписки Claude там нет и не будет. Сейчас Claude на маке выключен, поэтому мак не показывает ни остатков, ни расхода Claude-аккаунта, на котором фактически работает команда. Причины:

1. Контракт v1 переносит через gist только расход (`days`). Проценты лимитов считаются «общими для аккаунта» и не синкаются (`docs/sync-protocol.md`, «What is shared»). Значит, машина без входа процентов не узнает.
2. На macOS выключенная подписка исключает и удалённый расход этого продукта (selftest `LimitsMonitor.swift` ~7108–7112, «remote history cannot restore disabled subscription»).
3. Headless `ccl-sync push --auto` (таймер 10 мин) лимиты не опрашивает. Опрос живёт только в PyQt5-трее, а на VPS PyQt5 и secretstorage нет.
4. `fetch_claude()` при истечении access-токена сам обновляет OAuth и переписывает `~/.claude/.credentials.json` (`linux/ccl/limits.py` 205–235). На VPS этот файл одновременно использует живой Claude Code. Так же `codex_access_token()` переписывает `~/.codex/auth.json` (там же, 518–538).
5. Расход в gist привязан к продукту, а не к аккаунту. Разные аккаунты одного продукта складываются в одну сумму.

### Целевые пользователи
- **Владелец на MacBook.** Входа Claude нет, есть или может быть вход Codex. За 5 секунд хочет понять, сколько осталось у Claude-аккаунта команды и хватит ли до сброса.
- **Владелец на ThinkPad ALSE (Linux-трей).** Тот же набор аккаунтов, другая машина. Вторая очередь, см. приоритеты.
- **Команда агентов на VPS** — косвенный пользователь. Она порождает расход, и ей нельзя ломать вход Claude Code / Codex и провоцировать ограничения Anthropic.
- **Системные роли:** издатель (машина со входом опрашивает и публикует) и читатель (любая машина показывает весь набор). Одна машина может быть и тем и другим.

### Бизнес-цели (SMART)
Окно замера — первые **14 дней после выкладки** издателя на VPS и читателя на маке. Дата старта = день выкладки, Юрка ставит напоминание в `HQ/now.md`.

| # | Цель | Метрика и порог | Способ замера |
|---|---|---|---|
| G1 | Не провоцировать Anthropic | 0 ответов 429 от `api.anthropic.com/api/oauth/usage`. 100% пар соседних запросов по одному Claude-аккаунту (суммарно по всем машинам, включая ручные обновления) идут с промежутком ≥ 900 с. В день без активности на сервере ≤ 10 запросов на аккаунт | Журналы попыток всех издателей (O1), сведённые по метке аккаунта |

| G3 | Свежесть на маке | Пока VPS онлайн, ≥ 95% времени карточка Claude-аккаунта на маке в состоянии «свежо» (V4). 10 из 10 ручных сверок владельца: время «данные от» ≤ интервал источника + 20 мин | Журнал O1 (интервалы между удачными опросами) и 10 ручных сверок с записью в протокол |

## 2. Обзор требования (≤30 слов)
Каждая машина со входом адаптивно опрашивает лимиты своего аккаунта и публикует их в gist. Каждая машина показывает карточки и расход всех аккаунтов набора.

## 3. Детальный дизайн

### Декомпозиция
- **Путь владельца:** установить издатель на VPS → VPS опрашивает и публикует → мак читает gist → видит карточку каждого аккаунта (остатки, сброс, темп, расход, деньги) → понимает свежесть → при необходимости обновляет → через 14 дней проверка гипотезы.
- **Роли:** владелец (настраивает видимость, подписи, локальный опрос), издатель (опрос + публикация), читатель (слияние + показ), соседние CLI на машине (Claude Code / Codex делят файлы входа).
- **CRUD ключевых объектов:**

| Объект | Create | Read | Update | Delete |
|---|---|---|---|---|
| Метка аккаунта (A1) | издатель при первом успешном чтении входа | все читатели | при смене входа на машине (новая метка, старая остаётся в истории) | не удаляется. Аккаунт без снимков 45 дней выпадает по правилу v1 |
| Подпись аккаунта (A3) | по умолчанию автоматически | все читатели | владелец переименовывает на любой машине | сброс к автоматической |
| Снимок лимитов (C2) | издатель после попытки опроса | все читатели | каждая попытка с новым результатом | продукт выключен или вход пропал → статус `signed_out`, значения не выдумываются |
| Расход по аккаунту (U1) | издатель из транскриптов | все читатели | каждый цикл 10 мин | окно 45 дней (v1) |
| Настройки видимости и опроса (N1–N2) | первый запуск или миграция | локально | владелец | — |

### F1. Идентичность аккаунта — P0
**User story.** As a владелец нескольких машин, I want чтобы каждый аккаунт узнавался одинаково на всех машинах, so that один аккаунт на двух машинах давал одну карточку, а разные аккаунты — разные.

**Бизнес-правила**
- **A1. Метка аккаунта.** У каждого снимка и каждой порции расхода есть стабильная метка аккаунта для пары (провайдер, аккаунт). Она одинакова на всех машинах с этим аккаунтом, разная для разных аккаунтов и не меняется при перевыпуске токенов.
- **A2. Приватность метки.** Метка псевдонимна: по ней нельзя восстановить email, имя, UUID организации или исходный идентификатор аккаунта без доступа к локальным файлам владельца. Открытые email, имя, `account_id`, `accountUuid` и тела токенов в gist не попадают. Конкретный способ (ключевой хеш, где лежит общий ключ) выбирает архитектура, проверяет SecurityAnalyst (T1).
- **A3. Подпись.** Подпись по умолчанию строится без ПДн: `<Продукт> <план> · <машины>`, например «Claude Max 20x · vps». Владелец может задать короткую подпись (≤ 32 символа) на любой машине. Она применяется на всех машинах набора. [доп.] Подпись хранится в gist; конфликт правок решается последней записью по времени.
- **A4. Источник идентичности** — локальные файлы входа: Claude — `accountUuid` из `~/.claude.json`, Codex — `account_id` из `~/.codex/auth.json` (подтверждено синтезом архитектуры, `arch/plan-synth.md`). Если локального источника нет, метки нет и действует A5. Запрос профиля «узнать, кто я» к Anthropic/OpenAI в первой поставке **не используется** (Could). Если он появится позже — не чаще 1 раза в сутки на аккаунт и в счёт бюджета B1.
- **A5. Неизвестный аккаунт.** Снимки и расход от старых версий (без метки) и от машин, где метку получить не удалось, относятся к группе «<Продукт> · аккаунт не указан». Её отображение описано в V7.
- **A6. Смена входа на машине.** Если на машине сменился аккаунт продукта, новые снимки и новый расход идут под новой меткой. Ранее посчитанный расход остаётся под прежней. Транскрипты CLI не содержат аккаунта, поэтому день, в котором была смена, относится к аккаунту, который был активен при индексации строки. [доп.] Точность границы — до цикла индексации. Правило атрибуции фиксирует архитектура.
- **A7. Один вход на продукт на машину.** Одновременно на одной машине у продукта не больше одного активного аккаунта (так устроены CLI). Несколько аккаунтов одного продукта на одной машине — не-цель.

**Исключения:** файл входа не читается, битый или в процессе записи → метки нет. Снимок публикуется под A5 со статусом ошибки, предыдущая метка не выдумывается. Метки у двух машин совпали, а планы различаются → это один аккаунт с разными показаниями по времени (правило V3), без предупреждения.

**Acceptance**
- Дано: Codex на маке и Codex на VPS вошли в **один** аккаунт. Когда мак слил gist, тогда показана **одна** карточка Codex с самым свежим показанием и подписью с обеими машинами.
- Дано: Codex на маке и на VPS — **разные** аккаунты. Когда мак слил gist, тогда показаны **две** карточки Codex с разными подписями. Расход и деньги у каждой свои.
- Дано: опубликованный файл машины. Когда тест ищет в нём email, `account_id`, `accountUuid`, `refresh`, `access_token`, `sk-`, путь `/home/` или `/Users/`, тогда совпадений нет.
- Дано: на VPS вышли из Claude и вошли в другой Claude-аккаунт. Когда прошёл цикл, тогда новые снимки под новой меткой, старый расход остался под старой, суммы не смешаны.

### F2. Контракт gist: снимок лимитов и расход по аккаунту — P0
**User story.** As a читатель на любой машине, I want получать из gist лимиты и расход каждого аккаунта с честной отметкой времени, so that показывать набор без собственного входа.

**Бизнес-правила**
- **C1. Совместимость.** Старые читатели (macOS ≤ 3.2.7, Linux ≤ 0.4.5) продолжают принимать файл новой машины и суммировать его `days` ровно как сейчас. Изменение аддитивное. Повышать `schema` так, чтобы старые читатели отбросили весь файл и потеряли расход, запрещено. Форму расширения (новый ключ в `machine-<id>.json` или отдельный файл) выбирает архитектура. Совместимость доказывается фикстурой в тестах обоих портов.
- **C2. Состав снимка на аккаунт:** провайдер; метка (A1); план и tier (для цены, U3); `asOf` — время **успешного** ответа API, а не время публикации; окна «сессия» и «неделя» с процентом и временем сброса; модельные окна (имя модели с бэкенда, процент, сброс), не более 8; у Codex — число сбросов (`reset credits`); расписание источника (режим Auto/фикс, текущий интервал, время следующей плановой попытки, признак backoff); `retryUntil` — дедлайн сервера, если получен 429/Retry-After; статус из закрытого перечня: `ok`, `stale`, `signed_out`, `expired`, `rate_limited`, `error`; время последней попытки.
- **C3. Последнее хорошее показание не стирается.** Неудачная попытка обновляет статус и время попытки, но сохраняет последние успешные значения с их `asOf`. Читатель показывает их с честным возрастом.
- **C4. Никаких выдуманных значений.** Если нет входа или продукт на машине не опрашивается, снимка аккаунта нет или его статус `signed_out`. Нулевых процентов «по умолчанию» нет.
- **C5. Расход по аккаунту.** Расход машины приписывается метке аккаунта (A6). Обратно совместимое суммирование `days` по продукту для старых читателей сохраняется (C1).
- **C6. Запись в gist.** Это по-прежнему целый идемпотентный снимок машины. Писать, только если изменился расход, снимок лимитов (новый `asOf`, статус или расписание) или подпись. Ещё одна разрешённая причина — heartbeat: в автоматическом режиме раз в 10 мин обновляется `lastSeenAt` машины, даже если больше ничего не изменилось. `lastSeenAt` входит в хеш снимка. `asOf` и расписание источника heartbeat не двигает. Причина: при Auto 4 ч и неизменном расходе файл иначе законно молчит часами, и состояние V5 №5 нельзя доказать. В остальных случаях без изменений запись пропускается. Чтение gist выполняется каждый цикл, как в v1.
- **C7. Границы и проверка у читателя.** Проценты — числа (не bool). Значение вне 0…100 отбрасывает окно. Время — ISO-8601 UTC. Строки (подпись, имя модели, план, tier) ограничены по длине и выводятся только как текст. Неизвестный статус = `error`. Битый снимок отбрасывается целиком, расход той же машины при этом принимается. Одна плохая запись не ломает слияние (как в v1).
- **C8. Описание.** Расширение описано в `docs/sync-protocol.md` для обоих портов, с примером JSON и правилами C1–C7.

**Исключения:** часы машины-источника спешат, и `asOf` в будущем больше чем на 5 мин → возраст считается 0, время показывается как есть, расчёт темпа запрещён (V6). Усечённый файл (`truncated`) читается по правилам v1. Ожидаемый размер файла не растёт больше чем на 4 КБ на аккаунт [доп.].

**Acceptance**
- Дано: файл машины нового формата и читатель macOS 3.2.7 / Linux 0.4.5. Когда идёт слияние, тогда расход этой машины учтён так же, как файла без расширения, ошибок нет.
- Дано: на VPS 401 после успешного чтения час назад. Когда издатель опубликовал снимок, тогда статус `expired`, значения и `asOf` прежние.
- Дано: в снимке процент `"80"` (строка), `true` или `140`. Когда читатель сливает файл, тогда окно отброшено, остальные окна и расход приняты, приложение не падает.

### F3. Headless-издатель на VPS и издатели на других машинах — P0 (VPS, macOS), P1 (Linux-трей)
**User story.** As a владелец, I want чтобы VPS без графики сам опрашивал лимиты своих аккаунтов и публиковал их вместе с расходом, so that команда на сервере была видна с любой моей машины.

**Бизнес-правила**
- **P1. Headless.** Издатель на VPS работает без PyQt5, secretstorage и сессии D-Bus, под `systemd --user` (Linger), без root. Токен GitHub хранится в существующем файловом бэкенде `0600` (S4).
- **P2. Установка.** Есть способ установить только издатель: без трея и автозапуска графики. Обычная установка с треем продолжает работать как раньше.
- **P3. Один опросчик на аккаунт на машине.** Если на машине одновременно работают трей и headless-издатель (на VPS есть XFCE на `:20`), лимиты каждого аккаунта опрашивает ровно один процесс. Общее сохранённое состояние опроса и блокировка не допускают двойного запроса. Кто из двух опрашивает, решает архитектура.
- **P4. Auto по умолчанию у издателя.** Headless-издатель по умолчанию работает в Auto (в трее Auto по умолчанию выключен: `common.py` `autoPoll: False`, README). Фиксированный режим допускает только 15/30/60/240 мин. Локальная активность по транскриптам **этой машины** будит опрос до 15 мин по существующему правилу (`polling.py` `local_activity`).
- **P5. Каждая машина со входом — издатель.** macOS-приложение публикует снимки своих локально опрашиваемых аккаунтов (например, Codex на маке) — P0, иначе не работают F1 и B2. Linux-трей делает то же — P1.
- **P6. Публиковать некуда — не опрашивать.** Если издатель на VPS не вошёл в GitHub или вход отозван, он не опрашивает Anthropic/OpenAI: опрос без публикации тратит бюджет. Если сбой GitHub временный (сеть, 5xx, backoff), опрос идёт по расписанию, а последнее показание уходит в ближайший удачный цикл.
- **P7. Продукты на сервере.** Какие локальные входы опрашивать, задаётся на сервере без GUI: командой CLI или в файле настроек (N2). Обновление — существующий `ccl-sync update`.

**Исключения:** нет файла входа → снимок не публикуется или публикуется со статусом `signed_out` (C4), в Anthropic/OpenAI запросов 0. Диск полон, и состояние опроса не сохранить → опрос **не выполняется** (иначе каждый перезапуск таймера давал бы новый запрос, см. B3), ошибка видна в `ccl-sync status`. Перезагрузка VPS → сохранённое время попытки соблюдается (`OnBootSec=2min` не даёт внепланового опроса).

**Acceptance**
- Дано: чистая Ubuntu без PyQt5. Когда установлен только издатель и выполнен вход в GitHub, тогда через ≤ 15 мин в gist появляется файл VPS со снимками Claude и Codex и расходом.
- Дано: на VPS одновременно работают трей и издатель. Когда проходит 2 часа при активной работе, тогда журнал показывает не более одного запроса к `oauth/usage` за любые 15 мин.
- Дано: издатель вышел из GitHub. Когда срабатывает таймер, тогда запросов к Anthropic и OpenAI нет, а `ccl-sync status` объясняет почему.
- Дано: мак с локальным входом Codex. Когда прошёл цикл синка, тогда в файле мака есть снимок Codex-аккаунта мака.

### F4. Бюджет опроса провайдеров — P0
**User story.** As a владелец, I want чтобы опрос лимитов был редким и адаптивным на всех машинах вместе, so that Anthropic не реагировал на частые запросы, а данные оставались достаточно свежими.

**Бизнес-правила** (одинаковы для `api.anthropic.com/api/oauth/usage` и `chatgpt.com/backend-api/wham/usage`, «провайдер» = любой из них):
- **B1. Пол на машине.** Не больше 1 запроса лимитов на аккаунт за 900 с на одной машине, учитывая все процессы, перезапуски, перезагрузки, таймер, трей и ручную кнопку «Обновить сейчас» (B8). Запрос обновления токена (`/v1/oauth/token`, `auth.openai.com/oauth/token`) тоже считается обращением к провайдеру. Его частоту ограничивает политика S1, но не чаще 1 раза на попытку.
- **B2. Пол на аккаунт по всем машинам.** Один аккаунт на нескольких машинах в установившемся режиме опрашивается не чаще, чем одной машиной по её Auto-расписанию. Если в gist уже есть показание этого аккаунта моложе текущего интервала машины, машина не опрашивает сама. **Как координироваться, решает архитектура.** Поскольку gist обновляется раз в 10 мин, архитектура обязана назвать и обосновать допуск переходного режима (запуск, смена входа, рассинхрон чтения gist). Допуск утверждает Юрка с владельцем до кода. Целевое правило — 0 пар запросов одного аккаунта ближе 900 с (G1).
- **B3. Попытка фиксируется до запроса.** Время попытки сохраняется на диск **до** отправки запроса. Если сохранить не удалось, запроса нет.
- **B4. Одна попытка = один запрос.** Нет немедленного повтора при ошибке, «прогревающих» и пробных запросов, параллельных запросов по одному аккаунту. Следующая попытка — только по расписанию.
- **B5. Алгоритм Auto не меняется.** Шаги 900/1800/3600/14400 с и переходы `PollState` (`linux/ccl/polling.py`: рост на шаг при низком расходе, сброс к 15 мин при расходе ≥ 1 п.п. за 15 мин или локальной активности, шаг вверх при ошибке) остаются как есть. Правило B2 — только **дополнительное условие пропуска** запроса, а не изменение шагов. [доп.] Нужно ли кормить Auto показаниями других машин из gist, чтобы расписание оставалось осмысленным при пропусках, решает архитектура. Порог «≥ 1 п.п. за 15 мин» и шаги не трогаются.
- **B6. Ошибки и Retry-After.** Любая неудачная попытка даёт backoff по `PollState`. Если пришёл 429/503 с `Retry-After` (или эквивалентный дедлайн), раньше этого времени запросов по аккаунту нет ни с одной машины: дедлайн сохраняется на диске (как `quotaServerRetryAt`) и публикуется в снимке (`retryUntil`, C2). Машины одного аккаунта его соблюдают. Ни Auto, ни таймер, ни ручная команда сервера его не сокращают. Если дедлайн дальше 24 ч, архитектура задаёт безопасную обработку, и это видно в `ccl-sync status`.
- **B7. Таймер 10 мин проверяет, а не опрашивает.** Тик без наступившего срока даёт 0 запросов к провайдерам. Фактическая задержка опроса лежит в пределах [интервал; интервал + период проверки]. При периоде 10 мин шаг «15 мин» фактически превращается в 15–20 мин. Это допустимо. Чаще проверять «пора ли» можно (сама проверка запросов не делает), решает архитектура.
- **B8. Ручное обновление.**
  - Аккаунт **без** входа на этой машине: «Обновить сейчас» не обращается к провайдеру ни с этой машины, ни через другую машину. Выполняется один внеочередной цикл чтения gist (GitHub) с защитой 30 с и backoff GitHub. Защита 30 с относится только к чтению gist.
  - Аккаунт **со** входом на этой машине (решение владельца 2026-10-12): «Обновить сейчас» обращается к провайдеру, только если с последней попытки по этому аккаунту на **любой** машине (своя попытка или попытка из снимка в gist) прошло ≥ 900 с и не действует `retryUntil`, полученный любой машиной. Иначе кнопка выполняет только чтение gist (защита 30 с) и показывает, когда опрос провайдера станет возможен. Прежняя 30-секундная защита для запроса к провайдеру отменяется. Ручные попытки помечаются в журнале O1 причиной `manual` и входят в G1 на общих основаниях.
  - Ручная команда headless-сервера (если появится) соблюдает пол 900 с без исключений.
- **B9. Нет входа или вход отключён** → 0 запросов к провайдеру по этому аккаунту.
- **B10. Читатель не опрашивает за других.** Машина никогда не запрашивает у провайдера лимиты аккаунта, на который на ней нет входа.

**Исключения:** часы VPS переведены назад → действует существующее правило коррекции `PollState.due` (`last_attempt > now` → now) без внепланового запроса. Сеть недоступна → неудача, backoff, без повторов. Gist не читается → B2 не может подтвердить свежесть показания другой машины, машина опрашивает по собственному расписанию в рамках B1. [доп.] Архитектура подтверждает, что это не нарушает G1.

**Acceptance**
- Дано: показание получено 5 мин назад, интервал 15 мин. Когда перезапускается процесс, срабатывает таймер или перезагружается VPS, тогда запроса к `oauth/usage` нет.
- Дано: ответ 429 с `Retry-After: 3600`. Когда через 15 мин наступает срок Auto или срабатывает таймер, тогда запроса нет до истечения часа, и мак с тем же аккаунтом тоже не запрашивает.
- Дано: на сервере нет активности 12 ч. Когда считаем журнал за сутки, тогда интервал вырос до 4 ч и запросов ≤ 10.
- Дано: Codex-аккаунт A есть на маке и на VPS, VPS опросил его 3 мин назад и опубликовал. Когда у мака наступил свой срок, тогда мак не опрашивает A, а показывает показание VPS.
- Дано: мак без входа Claude, карточка Claude с VPS. Когда владелец жмёт «Обновить сейчас», тогда мак делает только чтение gist, к Anthropic запросов 0.

### F5. Входы на машинах и данные в gist — безопасность — P0
**User story.** As a владелец, I want чтобы публикация лимитов не ломала вход Claude Code и Codex на сервере и не выносила секреты в gist, so that команда на VPS работала без сбоев, а gist оставался безопасным.

**Бизнес-правила** (требования, не решения; проверяет SecurityAnalyst на T1):
- **S1. Живой вход не теряется.** Работающие на VPS Claude Code и Codex CLI ни разу не теряют вход из-за издателя: ни одноразовый refresh-токен не расходуется так, что CLI останется с недействительной парой, ни файл входа не переписывается в несогласованном виде. **Решение владельца 2026-10-12:** на машине, где файл входа делит живой CLI, действует политика «только чтение». Издатель не обновляет OAuth-токены и не переписывает файлы входа, а ждёт, пока CLI обновит их сам. Механизм реализации выбирает архитектура, проверяет SecurityAnalyst (T1). Следствие: если токен истёк, издатель не делает запрос, публикует статус `expired`/«ждём обновления входа на машине» и последние значения с честным `asOf` (C3). Данные «замерзают», пока CLI простаивает. Владелец это принял.
- **S2.** S1 действует и на macOS (Codex), и на Linux-трее, если там тоже работает живой CLI. Действующие защиты (`_PENDING`, перечитывание перед записью, `deadRefresh`) не ослабляются.
- **S3. Минимизация в gist.** В gist попадают только поля C2, метка A1 и подпись A3. Не попадают: токены, отпечатки токенов, email, имя, идентификаторы аккаунта/организации в открытом виде, промпты, пути, имена проектов, хосты, тексты ошибок (только перечислимый статус). Это проверяет автотест на запрещённые ключи и шаблоны.
- **S4.** Токен GitHub на headless VPS хранится только в файловом бэкенде `0600`. Его нет в argv, окружении дочерних процессов, журналах, `ccl-sync status` и gist.
- **S5.** Журналы издателя (O1) не содержат токенов, заголовков авторизации и тел ответов.
- **S6.** Читатель считает снимки недоверенными данными (C7). Подписи и имена моделей выводятся как текст и не исполняются.

**Acceptance**
- Дано: Claude Code на VPS активно работает, издатель включён 14 дней. Когда владелец открывает сессию Claude Code в любой момент, тогда повторного входа не требуется. Журнал O1: записей издателя в файлы входа 0.
- Дано: access-токен Claude на VPS истёк, а политика — «только чтение». Когда наступил срок опроса, тогда запросов к `/v1/oauth/token` и `oauth/usage` нет, снимок со статусом `expired` и прежним `asOf`, на маке видно «на машине vps нужно обновить вход Claude Code». Команда `claude login` на маке **не** предлагается (урок 012).
- Дано: опубликованный файл и журнал издателя. Когда их сканирует тест S3/S5, тогда запрещённых данных нет.

### F6. Вид по аккаунтам на читателе — P0 (macOS), P1 (Linux-трей)
**User story.** As a владелец на MacBook без входа Claude, I want видеть карточку Claude-аккаунта команды с остатками, сбросами, свежестью и прогнозом, so that управлять расходом команды, не заходя на сервер.

**Бизнес-правила**
- **V1. Одна карточка на аккаунт.** Читатель показывает по карточке на каждый видимый (N1) аккаунт набора. Это аккаунты со входом на этой машине (локальный опрос) и аккаунты без входа на этой машине (из gist). Один аккаунт на нескольких машинах даёт одну карточку.
- **V2. Порядок** [доп.]: Claude-аккаунты над Codex (как сейчас), внутри продукта первым идёт аккаунт с локальным входом, затем остальные по подписи. При большом числе карточек размеры, прокрутку и вид Simple/Advanced определяет UX.
- **V3. Самое свежее показание.** Для аккаунта берётся успешное показание с наибольшим `asOf` среди всех машин, включая свою. При равенстве побеждает локальное. Неудачный снимок не вытесняет более свежий успешный, но его статус учитывается в V5.
- **V4. Свежесть и источник.** Если показание пришло с другой машины, на карточке видны источник и время: «данные с <машина> от HH:MM» (часовой пояс читателя). Карточка «свежая», пока `now ≤ следующая плановая попытка источника + 20 мин` (10 мин на тик таймера и 10 мин на синк читателя). Без расписания источника — пока `now − asOf ≤ интервал источника + 20 мин`. Действующее правило «снимок допустим до 4 ч» для показаний других машин **не применяется**: при Auto 4 ч оно ложно состарило бы нормальные данные. Расписание источника видно в подсказке.
- **V5. Состояния карточки аккаунта без входа на этой машине.** Каждое со своим текстом, тексты пишет UX:
  1. свежо;
  2. устарело: источник опрашивает, но показание старше порога;
  3. на машине-источнике проблема со входом (`expired`/`signed_out`) — рекомендация относится к той машине, а не к читателю;
  4. источник получил ограничение провайдера (`rate_limited`, до HH:MM);
  5. машина-источник не на связи: её `lastSeenAt` (heartbeat C6) старше 30 мин. Возраст `updated` файла для этого не используется;
  6. сам читатель не синхронизируется — действующий баннер синка v1;
  7. читатель не вошёл в GitHub — объяснение, что аккаунты без входа на этой машине видны только при входе в GitHub.

  Во всех состояниях последние значения видны с возрастом (C3). Возраст или сбой не выдаётся за истёкший вход (урок 012).
- **V6. Сбросы и темп.** Если время сброса окна прошло после `asOf`, окно показывается как сброшенное по действующей логике, старый процент не выдаётся за текущий. Темп и прогноз («Хватит до сброса» / «Кончится в HH:MM») считаются как у локальной карточки, но от момента `asOf` показания и с пометкой его времени. При невалидном `asOf` (в будущем больше чем на 5 мин, нет) темп не считается: «Нет свежих данных · темп не считаем».
- **V7. «Аккаунт не указан».** Расход старых машин без метки (A5) показывается отдельной группой «<Продукт> · аккаунт не указан (<машины>)». Он не вливается в известный аккаунт и не теряется. Карточки лимитов у такой группы нет: снимков старые версии не публикуют. Скрытие — по N1. Решение владельца 2026-10-12: владелец обновит приложение на всех машинах. Группа остаётся переходным поведением и по умолчанию показывается.
- **V8. Строка меню.** Числа в строке меню берутся у выбранного аккаунта продукта. По умолчанию это аккаунт с локальным входом, без него — первый по V2. Владелец может выбрать другой. Устаревшие числа аккаунта без входа на этой машине помечаются так же, как устаревшие локальные. Подтверждено владельцем 2026-10-12.
- **V9. Футер Auto** показывает интервалы только **локально опрашиваемых** аккаунтов. Аккаунты без входа на этой машине не выдаются за опрашиваемые ею. Их расписание видно в подсказке карточки.
- **V10. Simple и Advanced.** Аккаунты без входа на этой машине видны в обоих видах (решение владельца 2026-10-12) (в Simple — проценты и сбросы, в Advanced — ещё темп, расход и деньги). Вход в GitHub на macOS сейчас доступен только в настройках Advanced (`syncBlockShown`). UX решает, как владельцу в Simple узнать, что для аккаунтов без входа на этой машине нужен вход в GitHub.
- **V11. Звуки** при сбросе и достижении лимита аккаунта без входа на этой машине — P2. Без повторного срабатывания на одно событие от разных машин.

**Acceptance**
- Дано: на маке нет входа Claude, VPS опубликовал Claude Max 20x 10 мин назад. Когда владелец открывает панель (Simple и Advanced), тогда видна карточка Claude с процентами сессии, недели и модельного окна, временем сброса и строкой «данные с vps от HH:MM». В Advanced видны темп, расход и деньги.
- Дано: Auto на VPS вырос до 4 ч, последний опрос 3 ч 50 мин назад, VPS на связи. Когда владелец смотрит карточку, тогда она не помечена как устаревшая.
- Дано: VPS выключен 40 мин. Когда мак синкается, тогда карточка в состоянии «машина vps не на связи с HH:MM» с последними значениями.
- Дано: показание с `asOf` 10:00, сброс сессии в 11:00, сейчас 11:20. Когда карточка рисуется, тогда сессия показана как сброшенная, а не со старым процентом.
- Дано: в gist есть старая Linux-машина 0.4.5 с расходом Codex без метки. Когда мак сливает gist, тогда этот расход отдельной группой «Codex · аккаунт не указан», суммы известных аккаунтов не изменились.

**User story.** As a владелец, I want видеть расход и стоимость отдельно по каждому аккаунту, so that понимать, сколько «стоит» команда на сервере против моей личной работы.

Цена подписки аккаунта:** (1) цена, заданная владельцем для этого аккаунта на читателе; (2) иначе по плану и tier из снимка аккаунта (`max_20x` → $200, `max_5x` → $100, `pro` → $20, Codex — по действующей таблице с пометкой «оценка»); (3) иначе действующий запасной вариант с пометкой «оценка». ### F8. Настройки: видимость и локальный опрос — P0
**User story.** As a владелец, I want отдельно решать, какие аккаунты показывать и какие локальные входы опрашивать, so that мак без Claude показывал Claude-аккаунт команды, но сам не лез в Anthropic.

**Бизнес-правила**
- **N1. Какие аккаунты показывать.** Список всех известных аккаунтов набора (подпись, план, машины). По умолчанию видны все, включая вновь появившиеся. Скрытый аккаунт исчезает из панели, строки меню и расхода на этой машине. Gist и другие машины это не затрагивает.
- **N2. Какие локальные входы опрашивать** — по продукту на этой машине (замена нынешних переключателей «Собирать и показывать»). Выключенный локальный опрос по-прежнему означает: 0 запросов к провайдеру, не читать файлы входа и Keychain (урок 013), не индексировать журналы этого продукта, не публиковать снимок. Аккаунты этого продукта без входа на этой машине при этом видны (по N1).

- Менять алгоритм Auto, шаги 15/30/60/240, порог активности, правила backoff `PollState`.
