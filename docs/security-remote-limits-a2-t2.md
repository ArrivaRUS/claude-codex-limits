## 3. Главный вопрос: может ли в `never` хоть один путь записать файл входа или потратить refresh-токен

**Нет — для попытки, закреплённой как `never`** (политика прочитана из `settings.json` в начале попытки под `quota`). Перечислил все пути по коду:
- **Одноразовый refresh-токен** уходит только в двух местах — `limits.py:320` (Claude) и `:718` (Codex); оба стоят за `if _ATTEMPT.policy != "guarded": return _cli_expired(...)` (`:309`, `:706`). В `never` — 0 POST при live/expiring/dead/absent/partial/empty (A2-01: `self.trap.posts() == []`), A2-09 (смена между попытками).
- **Replay `_PENDING`**: `p = _PENDING.get(...) if _ATTEMPT.policy == "guarded" else None` (`:282`, `:683`) — в `never` старая запись не исполняется и не подменяется (A2-03 проверяет `assertIs`), маркер не создаётся.
- **`_save_claude_tokens`/`_save_codex_tokens`/`_rewrite_json`** при прямом вызове → `refused`/исключение + `policy_violation`, файл не тронут, `deadRefresh*` не меняется (A2-02; `assert_untouched` = байты, `mtime_ns`, inode).
- **`deadRefresh`/`deadCodexRefresh`**: читаются/пишутся только в guarded-ветках (`:318`, `:331`, `:338`, `:715`, `:726`).
- **`~/.claude.json`**: в `linux/ccl/` ни одного пути записи (grep `CLAUDE_JSON` → только `accounts.py:41` чтение `open(path, "rb")`).
- **Гонки с CLI**: в `never` файл только читается (5×0,2 с, `:173–189`) — состояние гонки сводится к «прочитали старую или новую пару», записи нет. CLI переписал файл между чтением токена и запросом → запрос уйдёт со старым access (ещё валиден до `expiresAt`) — не трата refresh.
- **Смена политики во время попытки**: `set_credential_write` ждёт `quota` ≤ 60 с (`common.py:389–393`); `flock` на разных fd конфликтует и внутри одного процесса, поэтому главный поток трея не обойдёт воркер. Внутри попытки `credential_write()` не перечитывается (`_write_allowed` смотрит пин). Смена `guarded → never` **посреди** guarded-попытки: попытка дописывает пару по старой политике (A2-09 `test_change_inside_attempt_does_not_apply_midway`) — по замыслу (П3-б.2).
- **`threading.local` `_ATTEMPT`**: второй поток не видит чужой пин; он ждёт `flock` и закрепляет свою политику. Исключение внутри попытки → `finally: del` (`:57–60`), `flock` снимается в `file_lock` (`common.py:143–146`).

**Три исключения — все по замыслу или за принятой границей, но их надо знать:**
1. **`flush_pending()` пишет файл при `settings.json = never`**, если в `_PENDING` лежит запись, рождённая guarded-сохранением (`policy == "guarded"`, `:378`; пин `_credential_attempt(policy="guarded")` `:374`). Проба P2: guarded-попытка с нечитаемым файлом → `_PENDING` (policy guarded) → правка `settings.json` руками на `never` (маркер обойдён — `set_credential_write` отказал бы) → попытка в `never` ничего не пишет и не трогает `_PENDING` → `flush_pending()` → **файл перезаписан ротированной парой**, событий O1 нет. Это и есть П3-б.2 (сервер уже ротировал пару; запись спасает вход CLI); но успех не журналируется (N3). Сегодня недостижимо — `flush_pending` никто не зовёт.
2. **Вложенный `flush_pending()` внутри чужой попытки в том же потоке** наследует её политику (`:47–50`), в `never` → `refused` → `policy_violation` + `pending_rotation_lost`, пара отброшена (Astra проверила: не молча). Production-вызова такого нет — A3 при подключении должен звать `flush_pending` **вне** попытки.
3. **Код того же UID в процессе**: `_rewrite_json_guarded` (`:250`), `_save_*_guarded`, `_credential_attempt(policy="guarded")` — обход без внешнего вектора; граница П3-в принята владельцем.

Для VPS (never + publisher, `--no-tray`) ни одно из трёх не достижимо: `flush_pending` не подключён, guarded-записей `_PENDING` возникнуть не может.

## 5. Находки (STRIDE-lite)

### N1 — major (guarded only) · Tampering/DoS на актив A-1 · отказ записи маркера после POST теряет уже ротированную пару
`limits.py:442–444` (Claude), `:625–627` (Codex): `_PENDING[p]` установлен → `common.write_rotation_marker(p)` → любой `OSError` (`EACCES`/`EROFS`/`ENOSPC` на `STATE_DIR`, нет `/proc/sys/kernel/random/boot_id`, `common.py:317–321`) вылетает из `_save_*_guarded` → `_save_*` ловит только `CredentialPolicyRefused` (`:432`, `:614`) → `_fetch_claude` → `fetch_claude()` (`:260–265`, тоже только `CredentialPolicyRefused`) → воркер трея получает исключение (`app.py:1293–1296` → «quota request failed»).
- **Проба P1 (код A2):** guarded, `expiring`, `STATE_DIR` 0500 при существующем `quota.lock` → 1 POST `/oauth/token` (refresh потрачен на сервере), `PermissionError`, **файл входа не изменён** (в нём старый, уже мёртвый refresh), пара только в `_PENDING`, маркера нет. **Код до A2 (`4a53ebf`) в той же пробе записал новую пару** (refresh-2 в файле). Регрессия против PRD S2 («действующие защиты не ослабляются»): CLI на этой машине при своём refresh получит `invalid_grant` → выход из входа. Повторные попытки в том же процессе бьются о тот же маркер, пока `STATE_DIR` недоступен; другой процесс при отсутствующем маркере переключит политику (`common.py:395–396`).
- **Серьёзность:** major (Astra: major, согласны). Не касается VPS (`never`).
- **Фикс:** отказ маркера после POST не должен прерывать сохранение — `try/except OSError` вокруг `write_rotation_marker` в обоих `_save_*_guarded`, дальше перечитывание и запись пары как обычно; при отказе и маркера, и записи пары — маркер повторяется на следующей попытке (replay уже делает это). Astra строже: если пара тоже не записалась, межпроцессный запрет переключения пропал — остаточное окно принять (требует одновременно недоступного `STATE_DIR`, нечитаемого файла входа и смены политики в этот момент) и отразить комментарием.
- **Тест-на-атаку:** оба продукта: `STATE_DIR` 0500 (lock существует) / `/proc` недоступен → guarded expiring → пара **записана**, исключения нет, `_PENDING` пуст; отдельно: маркер упал **и** файл нечитаем → `pending`, без исключения.

### N2 — major (строже из двух; моя оценка minor) · Tampering · маркер снимается без проверки владельца
`limits.py:292`, `:696` (CLI обновил пару сам → `remove_rotation_marker`), `:450`, `:634` (`superseded`), `:456`, `:640` (`saved`), `:392` (`flush_pending`) — удаляют **единственный** маркер продукта, хотя его мог записать другой процесс со своей незавершённой парой (`write_rotation_marker` перезаписывает чужой, `common.py:342`). Сценарий Astra (подтверждён по коду, многопроцессный тест не гонялся): процесс A оставил pending; внешний повторный вход; процесс B ротировал и оставил pending (маркер теперь B); A на следующей попытке видит «CLI обновил сам» → снимает маркер B; процесс C включает `never` при живой паре у B.
- **Серьёзность:** Astra — major; я — minor: нужны ≥ 2 guarded-процесса с попытками (в A2 попытки делает только трей, `app.py:1292`; издатель — forced never), внешний повторный вход и нечитаемый файл у B. По правилу «строже из двух» — **major**, но срок — на решение Юрки (фикс дёшев).
- **Фикс:** маркер на процесс — `rotation-pending-<product>-<pid>` (или удалять только при совпадении `pid`+`boot_id` с собой); `rotation_marker_live` сканирует все маркеры продукта; `write_rotation_marker` не перезаписывает чужой.
