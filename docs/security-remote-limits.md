## 4. Вердикт по восьми поверхностям
### П1. Метка `HMAC_SHA256(K, "ccl-account-v1|"+product+"|"+uuid)[:16]`, `K = SHA256("ccl-label-key-v1|"+gist_id)` — **minor (принять)**
Почему: против «читателя содержимого gist» ключ из id и случайный ключ эквивалентны — id у него уже есть, а прообраз (UUID v4, 122 бита) не перебирается; против «утечки id без содержимого» — id gist и так открывает содержимое (секретный gist читается по URL), так что новой поверхности метка не создаёт.
Случайный ключ Astra защищает только от актора, у которого **одновременно** есть UUID-кандидат (отдельная утечка: диагностический отчёт, issue с фрагментом `~/.claude.json`, база провайдера) и содержимое gist, — он подтвердит «этот аккаунт = этот расход». Это **принятый риск корреляции** (решение Юрки), а не криптографическая эквивалентность; ни один из вариантов не аутентифицирует снимки (писатель gist может скопировать метку). Замена дешёвая: интерфейс `label(id, key)` не меняется.
Условия: домен-разделение по продукту и версии есть; 64 бита хвоста при ≤ 8 аккаунтах — коллизии нет; UUID нормализовать (нижний регистр, strip) до HMAC — иначе две машины дадут разные метки одного Codex.
Находка П1-а (minor, целостность): запасной источник `organizationUuid` — метка организации **общая для всех членов организации**: два разных Claude-аккаунта одной организации сольются в одну карточку (V3 смешает показания). Фикс: запасной источник убрать → `label: null`, `labelReason: no_account_uuid`.
Находка П1-б (minor): смена gist (сход к раннему / пересоздание) меняет метки; индекс расхода хранит `labels[product][day] = label` → старые дни уйдут под «старой» меткой как **фантомная вторая запись продукта**. Фикс: в локальном индексе хранить исходный id (локальный файл 0600, он и так в `~/.claude.json`), метку считать при публикации.
Проверка: §6 Т1–Т3.

### П2. `~/.claude.json` как источник идентичности + привязка к поколению `.credentials.json` — **major (поднято с minor по Astra: нет сквозной привязки)**
Почему: подмена файла возможна только тем же пользователем (CLI, агенты) — уровень доверия всего `$HOME`. Рассогласование (issue #81231) даёт неверную **атрибуцию**, не утечку, но она бьёт по показаниям **и по координации B2** (пропуск по чужой метке). Отпечаток `sha256(refreshToken)[:16]` — локально в state 0600 (как `deadRefresh`) — приемлемо при запрете на выход из машины.
Находка П2-в (major, Astra, подтверждено по коду): нет сквозной привязки «файл входа → запрос → результат → кэш → метка». Метка считается при сборке блока (шаг 6), токен читался на шаге 5: смена аккаунта A→B во время HTTP даст показанию A метку B. Кэш провайдера ключуется только по продукту (`limits.py:626–628`, `select_snapshot`/`fallback` `quota_refresh.py:162–186`): после смены входа C3 «последнее хорошее показание» подставит значения A в запись B. Фикс: идентичность (id, метка) снимается **одним чтением** вместе с токеном и едет в `LimitData`; `cache.json`/`publisher-state.json`/`history` — по ключу `(product, label)`; fallback, попытки и `retryUntil` — только внутри той же метки; несовпадение метки до/после запроса → результат отброшен как `identity_changed`, запрос считается потраченным.
Находка П2-а (minor, доступность атрибуции): «поколение = mtime+size+sha256(refreshToken)» меняется при **каждом** обновлении access-токена/ротации refresh (каждые часы), а `oauthAccount` CLI обновляет только при запросе профиля → метка будет регулярно уходить в `null` без смены аккаунта. Фикс: поколение привязывать к смене **аккаунта**, не токена: сравнивать `oauthAccount.accountUuid` + `profileFetchedAt` (поле есть) с моментом смены `refreshTokenExpiresAt` «назад→вперёд» (новый вход), а не с mtime. Решает архитектор; тест фиксирует поведение.
Находка П2-б (minor): читать из `~/.claude.json` **только** `oauthAccount.accountUuid` (+`profileFetchedAt`); остальные поля `oauthAccount` (email, имя, организация) не должны попадать даже в локальные структуры издателя/журнал/`status`. `~/.claude.json` большой — парсить с лимитом размера (≤ 8 МБ) и `RecursionError`.
Проверка: §6 Т4–Т6, Т29.

### П3. Политика `credential_write: never` — **major (четыре требования закрыть до среза A/C)**
Почему: сама политика верна и реализуема одним guard'ом; но (1) путей записи больше, чем два POST, и (2) класс «горячее переключение» надо закрыть механизмом, а не окном (урок 008).
Пути записи в файлы входа по коду: Linux — только `_rewrite_json` из `_save_claude_tokens` (`limits.py:282–306`) и `_save_codex_tokens` (`:454–476`), вызываемых из refresh-ветки **и из replay `_PENDING`** (`:187–199`, `:497–510`). macOS — `codexAccessToken()` **`LimitsMonitor.swift:527–528`: прямая, неатомарная `try? out.write(to:)` в `auth.json`** без перечитывания/слияния (у Linux-порта это есть); Claude — `quotaReconcilePendingCredential` → `quietUpdate` → `persistClaudeQuotaUpdate` (Keychain-запись через helper `update quiet`, `QuotaRefresh.swift:300–325`, `LimitsMonitor.swift:276`).
Находка П3-а (major): macOS Codex пишет `auth.json` неатомарно и без слияния — при живом Codex CLI на маке это ровно S1-сценарий (половинчатый файл / перезапись чужой пары). Фикс: guard политики **до** POST и **в** функции записи; в `guarded` — атомарная запись + перечитывание/сравнение пары, как в `_save_codex_tokens`.
Находка П3-б (major, класс гонок; уточнено по Astra): переключение `guarded → never` при непустом `_PENDING` (только в памяти, `limits.py:257–261`) оставит уже ротированную на сервере пару незаписанной → CLI теряет вход; **перезапуск процесса её тоже уничтожает**, поэтому «политика фиксируется при старте» — необходимое, но не достаточное условие. Фикс: (1) политика читается один раз при старте процесса и неизменна до его конца (издатель — oneshot, `_PENDING` пуст по построению); (2) порядок переключения: процесс в `guarded` перед выходом/сменой политики **завершает replay `_PENDING`** (одна попытка записи по старой политике), иначе пишет `pending_rotation_lost` в O1 и показывает владельцу «возможен повторный вход CLI»; (3) `install.sh --publisher` на машине с запущенным старым треем (`:20`, код 0.4.5 с refresh в `guarded`) **требует остановить трей до включения** — старый процесс новый замок и политику не соблюдает; (4) guard в `_save_*` — второй рубеж: `policy_violation` в O1, результат `error/credentials`.
Находка П3-в (major → честно о границе, Astra): флаг `credential_write` в `settings.json` пишется любым процессом пользователя; принудительный `never` при `publisher: true` (значение `guarded` игнорируется, событие `policy_forced_never` в O1 и строка в `status`) — защита **от ошибочной настройки и одной правки**, не граница против агента того же UID: он может менять код в `~/.local/share`, юнит, сами файлы входа. Граница UID принимается владельцем как есть (как в v1 для токена GitHub); журнал того же UID — не независимое доказательство для G2 (сверка `stat` файлов входа Юркой — §7).
Находка П3-д (major, Astra, строже плана): `never` должен зависеть от **факта совместного использования файла входа**, а не от `publisher: true`. PRD S2 распространяет S1 на macOS Codex и Linux-трей при живом CLI; `plan-claude.md:184` оставляет им `guarded`, а `guarded` по построению не CAS с CLI (`limits.py:282–286`: «a writer after this read can still race replace») и не защищает от одноразового расходования refresh-токена параллельно с CLI. Фикс: `never` — значение по умолчанию **на всех портах**; `guarded` — явный opt-in владельца (настройка + строка в `status`), допустимый только там, где CLI на машине не используется.
Находка П3-г (minor): в `never` не трогать `deadRefresh`/`deadCodexRefresh`, не создавать `_PENDING`; `expiring` при Codex — JWT `exp` без запаса: 0 запросов, `cli_refresh_pending`.
Проверка: §6 Т7–Т11, Т33.

### П4. Минимизация в gist (S3) — **major (существующая утечка имени + расширить скан)**
Почему: состав записи §A + З2 секретов не содержит; но v1 уже публикует `Host.current().localizedName` (`LimitsMonitor.swift:2037`, «MacBook Pro — Алекс») и `socket.gethostname()` (`common.py:302–304`) — имя владельца и хост VPS лежат в gist **и в истории ревизий**, санитизация вперёд историю не чистит.
Что ещё нельзя класть: `organizationUuid`/`organizationName`/`emailAddress`/`fullName` (есть в `~/.claude.json`), `id_token`/`access_token`/`eyJ…` (JWT), `scopes`, `refreshTokenExpiresAt`, отпечатки токенов (`deadRefresh`, отпечаток поколения), любой UUID кроме `machine.id`, тексты ошибок/исключений, пути, hostname целиком, `OPENAI_API_KEY` (ключ есть в `~/.codex/auth.json`!).
Находка П4-а (major, существующая): `machine.name` с именем владельца — закрывается F.1 п. 1 плана (тег `[a-z0-9-]{1,16}`); дополнительно для `--publisher` тег задавать явно (`--name vps`), запасной `linux` — первая DNS-метка VPS часто содержит id у хостера.
Находка П4-б (minor, решение владельца): после выкатки **пересоздать gist** (удалить старый) — это единственный способ убрать имя из истории ревизий; метки при этом сменятся у всех машин одновременно (см. П1-б).
Находка П4-в (minor): `captions` ≤ 32 символов — убрать `Cc`/`Cf` (управляющие, bidi-override, zero-width), NFC, отклонять `@` и `/` (email/пути) при вводе; `models[].name` с бэкенда — та же чистка, ≤ 48, у писателя **и** у читателя.
Находка П4-г (minor): `tz` (v1) — грубая геолокация; принято в v1, оставить.
Проверка: §6 Т12–Т14.

### П5. Читатель как потребитель недоверенных снимков (C7) — **major (четыре конкретных вектора)**
Почему: план C7 покрывает типы/диапазоны, но не покрывает: (а) **URL клика** по чужой карточке — должен быть константой продукта, не полем снимка; (б) Linux-трей: `QLabel`/rich text — подпись `<img src="http://…">` в `Qt::AutoText` вызывает загрузку/рендер HTML → `setTextFormat(PlainText)` или только `drawText` (`paint.py`); (в) Python `json.loads` принимает `NaN`/`Infinity` → `pct` «число», но не конечное → `isfinite` обязателен (Swift отвергает сам); (г) `_raw()` читает тело `raw_url` **без лимита** (`sync.py:717`, `common.http` → `r.read()`): писатель с токеном подсунет гигабайт → OOM читателя; при лимите расширения 8 MiB читать `read(cap+1)` и отбрасывать.
Также: даты — Linux `parse_iso` уже ограничивает год 4 цифрами и ловит `OverflowError` (`common.py:353–381`), Swift — проверить тем же тестом; дубли записей `(product,label)` в одном файле → брать максимальный `asOf`; `captions` — карта не более 64 ключей, ключи = 16 hex; `accounts` ≤ 8, `models` ≤ 8, глубина — `RecursionError`/`JSONSerialization` как в v1; `String(format:)` со строками снимка запрещён; проекция З2 — складывать **либо** `accounts[].days`, **либо** корень, никогда оба.
Находка П5-д (minor, Astra, подтверждено): лимита одного raw-файла мало — `common.http` читает любое тело без предела (`common.py:427–432`, в т.ч. тела ошибок), все файлы gist копятся до merge (`sync.py:711–725`, `LimitsMonitor.swift:2694–2700`). Нужны пределы: число файлов `machine-*` ≤ 64, суммарно ≤ 64 MiB, тело любого ответа ≤ 16 MiB, разобранных записей и время прохода ограничены.
Находка П5-е (minor, Astra, подтверждено): старые поля `machine.name/os/app` принимаются без чистки (`sync.py:382–384`) и печатаются в терминал `ccl-sync status` (`cli.py:292–294`) → управляющие последовательности терминала из gist. Фикс: у читателя `Cc`/`Cf` убрать, ≤ 64 символов, для всех строк `machine.*` — не только новых полей.
Реалистичная цепочка: prompt-injection у агента на VPS → `~/.config/claude-codex-limits/github-token` → PATCH враждебного `machine-*.json` → читатель на маке. Поэтому «свой gist» ≠ доверенный.
Проверка: §6 Т15–Т19, Т30.

### П6. Headless VPS: таймер, журнал O1, `status`, `install.sh --publisher --no-tray` — **minor (ок с проверками)**
Почему: `ExecStart=… ccl-sync push --auto --quiet` — без токена в argv/env (проверено `install.sh:78–86`); токен только в `CONFIG_DIR/github-token` 0600 (`vault._file_set` → `write_atomic` 0600, каталоги 0700 `ensure_dirs`); `status` печатает путь к файлу и gist-URL, не токен (`cli.py:233–235, 250`); `common.http` не кладёт заголовки в текст ошибок.
Находка П6-а (minor): `publisher.jsonl` — открывать `os.open(..., O_APPEND|O_CREAT, 0o600)`, не полагаться на umask; ротация — атомарная перезапись 0600. Трейсбек необработанного исключения уходит в journald (локально, читаем владельцем) — допустимо, но `publisher.run_pass` должен ловить всё и писать класс события, не текст.
Находка П6-б (minor): `status` показывает gist-URL — это capability-ссылка на всё содержимое; оставить (v1), но не копировать в отчёты/чаты агентов. `~/.codex` 0755 — файлы 0600, но листинг каталога виден другим пользователям VPS; рекомендовать владельцу `chmod 700 ~/.codex` (вне скоупа кода).
Находка П6-в (minor): `--no-tray` не должен создавать `.desktop`/autostart (сейчас `install.sh:60–72` создаёт всегда); `XDG_RUNTIME_DIR` экспортировать только если каталог существует.
Проверка: §6 Т20–Т22.

### П7. Координация B2 (вариант A) через gist: доверие к чужим `asOf`/`attemptAt`/`retryUntil`/`nextAt` — **major (ограничить доверие во времени)**
Почему: чужие поля могут только **откладывать** мой опрос (пропуск не двигает `last_attempt`, `observe` чужими не кормим — B5) и никогда не учащать его сверх моего Auto: ручное правило `max(local, чужой asOf)+900 ≤ now` тоже лишь удлиняет. Значит «опрашивать чаще» через gist невозможно — это доказуемо чистым `coordination.decide`. Но план `plan-claude.md` §D: «чужой `asOf` в будущем = возраст 0 → пропуск» — при `asOf = 2099` (часы, баг, враждебный файл) моя машина **не опросит никогда**, пока файл лежит в gist; то же `attemptAt` (З3) и `retryUntil` (З5 «не обрезать» писалось про **свой** ответ сервера).
Фикс (границы доверия в `decide`; уточнено по Astra): чужой `asOf`/`attemptAt`/`nextAt` > `now + 60 с` или несогласованные между собой → запись для B2 **не свежая** (для показа — возраст 0, V6 остаётся); чужой `retryUntil` хранится **отдельно** от собственного (`remote_retry_until`, не в `server_until`/`AutoPollState.serverRetryAt`, как сейчас в `plan-claude.md:176` — иначе недоверенный дедлайн превращается в «свой без ограничения»); его потолок привязан к моменту **первого принятия** события: `effective = min(retryUntil, firstSeenAt + 24 ч)`, `firstSeenAt` сохраняется на диске (пересчёт от `now` при каждом чтении дал бы вечное ожидание); далее — своё расписание и событие `remote_retry_capped` в O1. Собственный серверный дедлайн — без потолка (З5), но проверяется на конечность/представимость. Чужие записи с `lastSeenAt` старше 30 мин в подавлении не участвуют; потеря heartbeat **не отменяет** уже принятого чужого ограничения до его `effective`. Тай-брейк по `machine.id` — задержка максимум на один тик.
Контрактное уточнение для PM/архитектора: настоящий чужой Retry-After на 48 ч будет сокращён до 24 ч вопреки букве B6 — это осознанная цена защиты от вечного пропуска; при сокращении машина делает ≤ 1 запрос по своему Auto, сервер при необходимости взведёт дедлайн снова (и он уже будет **своим**, без потолка).
Инварианты для теста: (И1) для любого чужого входа число моих запросов за 24 ч ≤ числа при одиночной работе по Auto; (И2) повторная доставка неизменного чужого события, heartbeat и рестарты **не продлевают** его эффективный дедлайн; (И3) чужие данные никогда не сокращают собственный Retry-After и локальный пол 900 с; (И4) чужое свежее показание подавляет меня только пока `asOf ≤ now + 60 с` и `now − asOf < I_мой + 60 с`. Инвариант «≥ 1 мой запрос в сутки при любом чужом вводе» **неверен** (здоровый соседний издатель законно подавляет меня постоянно — это и есть B2) — снят.
Остаточный риск (принят владельцем с вариантом A): при длительной недоступности gist обе машины идут по своему Auto — близкие пары возможны ≤ 1 на 15 мин простоя (`plan-claude.md:171`); злоумышленник с токеном, публикующий правдоподобные свежие снимки, подавляет мой опрос — это целостность gist, не координация.
Проверка: §6 Т23–Т25, Т31–Т32.

### П8. Режим `delegated` трея и кнопка «Обновить» → проход издателя — **minor (схема верна, гонки закрываются замком)**
Почему: один код прохода под `file_lock("quota")`, удерживаемым через чтение состояния → решение → `begin` → сохранение → HTTP → результат (шаги 3–6), второй процесс после захвата перечитывает `PollState` с диска и видит `not_due`. Кнопка в трее — тот же проход с `manual=True`, под тем же замком; ручное правило B8 только удлиняет.
Находка П8-а (minor): внутри прохода `sync_cycle` берёт `file_lock("sync", blocking=False)` — если в этот момент синк трея (свой 10-мин таймер) держит `sync`, издатель получает `busy` → «gist не прочитан» → опрос по своему расписанию, лишняя близкая пара. Фикс: на машине с `publisher: true` трей не ведёт собственный синк (delegated и для синка) либо издатель ждёт `sync` с таймаутом (≤ 60 с), а не пропускает.
Находка П8-б (minor): замок общий только при **одинаковых** `XDG_CONFIG_HOME`/`XDG_STATE_HOME` у systemd --user и у сессии XFCE `:20`; расхождение = два состояния = двойной опрос. `ccl-sync status` и трей должны показывать путь state-каталога; тест сверяет.
Находка П8-в (minor): spam кнопки — `admit` трея возвращает `delegated`/`in_flight`, второй клик не стартует второй воркер; `save_poll_states` до `Thread.start` и ошибка записи = запроса нет (З8).
Проверка: §6 Т26–Т28, Т34.
