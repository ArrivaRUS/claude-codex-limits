## Заявленное разработчиком

1. **`build_opener` + `_HTTPDeadlineResponse`/`_HTTPDeadlineHandler`.** Корректно. Подклассы `HTTPHandler`/`HTTPSHandler`
   вытесняют стандартные в `build_opener`. Kwargs у `do_open` пробрасываются как есть, поэтому изменения `check_hostname` в
   3.12 не мешают. Сигнатура `HTTPResponse.__init__` одинакова в 3.7–3.14. `_tunnel` (CONNECT через прокси) тоже использует
   `response_class` и читает через обёрнутый `fp` — работает. Если `begin()` падает, ответ закрывается, утечки fd нет.
   Для вызовов без `deadline=` срок после заголовков снимается. Цепочка повторных `100 Continue` ограничена.
   Политика редиректов не изменилась: `_NoRedirect` / `_GistRawRedirect` / стандартный обработчик.
   Остаток на 3.7–3.9 (было до дифа): `socket.timeout` там не является `TimeoutError`, поэтому срок по таймауту сокета
   уходит в ветку «нет связи», а не в `HTTP_DEADLINE`.
2. **`_GistRawRedirect` без `deadline`.** Приемлемо. Все прыжки делят один `header_deadline` из `http()`. Тела промежуточных
   ответов не читаются. Прыжков ≤ 3. Худший случай — ≈ timeout + 3 соединения по timeout. На практике путь не встречается:
   `_raw` вызывается только в `_sync_cycle` под `_read_budget`, значит `deadline` там есть всегда.
3. **Пробельный `accessToken`.** Не закрыт (n1).
4. **Убран сброс серии после heartbeat.** Ложный запасной путь есть (P1).

## Находки

- **P1 · minor (Codex: major)** `publisher.py:421-424` и `:373`. Серия больше не обрывается успешными промежуточными
  тиками, а протокол требует «3rd consecutive publish_failed tick» (`sync-protocol.md:460`).
  Воспроизведение (Codex воспроизвёл): 2 тика с неудачным объявлением → тик `fresh_remote`/skip с успешным heartbeat →
  первая же следующая неудача даёт 3 и fallback. Второй путь: сброс на `:373` есть только в памяти до `_save` после
  провайдера. Если проход убит во время запроса провайдеру, на диске остаётся старый счётчик, и heartbeat его уже не
  обнулит.
  Почему у меня minor: ошибка ведёт к лишнему опросу, а не к голоданию. Fallback — штатный режим «gist недоступен»:
  самое большее 2 опроса без объявления на одну залежавшуюся серию. G1 под риском только при параллельном опросе
  соседа. Токенов и записи в файлы входа это не касается.
  Фикс: сбрасывать на успешном heartbeat, если в этом проходе не было неудачи объявления
  (`not reopened and not failed_this_tick`); сохранять 0 сразу после успешного PATCH №1, до провайдера.
  Тест: «2 неудачи → успешный heartbeat → 1 неудача → нет fallback».
- **P2 · minor (Codex, подтверждаю)** `common.py:933` → `except Exception` (`:1019`). Если PATCH вернул 2xx, а эхо оборвано
  по Content-Length, получается `Resp(0)` без `original_status`, и `sync.py:150` не может признать запись. Издатель
  откатывает попытку, которая уже объявлена в gist. Это фантомная попытка того же класса, что N4, в пределах П7.
  Фикс: ловить `IncompleteRead` в `http()` → `Resp(0, …, "incomplete body", original_status=r.status)`, и в `gh()` для
  PATCH с 2xx считать запись подтверждённой. Для GET поведение оставить.
- **n1 · nit** `limits.py:299`. `"   "` и истинные не-строки (`5`, `[1]`) проходят предпроверку → лишние `begin` и
  PATCH №1. Без refreshToken пробельный токен уходит в HTTP, а число даёт `TypeError` в `fetch_claude` — это было до дифа.
  Фикс: `_credential_block_complete(oauth, ("accessToken",))`, как в потребителе.
- **n2 · nit** `common.py:975`. Срок заголовков считается от начала `http()` и включает connect/TLS/отправку. Для OAuth POST
  это новый вид отказа относительно версии до A3 (окно узкое; потеря одноразового refresh — N2-класс). Фикс в A4: отсчитывать
  от конца отправки запроса или дать токен-эндпоинтам запас.
- **n3 · nit (Codex)** `common.py:838-860`. `_HTTPDeadlineStream` не делегирует `fileno()`. Потребителей нет.
