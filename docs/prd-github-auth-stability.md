# GH-AUTH-STABILITY — GitHub подключён месяцами без ручного перевхода

2026-10-04. Роль: ProductManager GPT-6.1 Sol/high. База чтения:
`297777d7b7386693fd8594a1b86532dab6b621c5`; production этой задачи ещё не начат.
Предыдущий [UI-план](github-auth-ui-fix.md) и
[диагностика](github-auth-diagnosis.md) — входные доказательства. Этот PRD
расширяет цель по прямому уточнению пользователя; улучшение текста само по
себе не является готовым решением.

## Цель и пользовательский сценарий

Пользователь один раз подключает GitHub, закрывает ноутбук, возвращается спустя
дни или недели и продолжает видеть расход с других компьютеров. При обычной
работе подключение сохраняется 30 и 180 дней без ручного входа, нового device
code, открытия браузера или подтверждения продления. Sleep, временное отсутствие
сети и поздний запуск/разблокировка хранилища не уничтожают действующий вход.

Успех — фактическая авторизованная синхронизация после автоматического
восстановления, подтверждённая воспроизводимыми тестами lifecycle обеих платформ.
Сохранённое имя пользователя или нейтральный заголовок без работающего доступа
не доказывает достижения цели.

## Допущения и внешние ограничения

- Реальная платформа, версия, настройка OAuth App и причина текущего случая
  ещё неизвестны. Они не блокируют поддержку двух режимов ответа issuer на
  macOS и Linux: долгоживущий access без refresh и короткий access с refresh.
- GitHub документирует expiring OAuth access на 8 часов и refresh, истекающий
  после 6 месяцев без использования. Device flow может выдавать оба токена;
  issuer возвращает сроки в полях ответа. Действующие долгоживущие выдачи не
  становятся короткими только от включения optional feature. Это внешняя
  policy, а не подтверждение режима нашего приложения.
  [GitHub: expiring access tokens](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#expiring-access-tokens).
- При успешном refresh прежние access/refresh перестают работать; выдаются новые.
  Если refresh уже истёк или недействителен, нужен новый пользовательский вход.
  Это делает потерю ответа после принятия одноразового refresh сервером
  отдельным риском.
  [GitHub: refreshing an access token](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#refreshing-an-access-token-with-a-refresh-token).
- 180 дней здоровой работающей сессии отличаются от 180 дней выключенного
  ноутбука. Нельзя обещать восстановление после срока действия неиспользованного
  refresh, внешнего отзыва, удаления локальных ключей пользователем или потери
  единственной новой пары, если issuer не предоставляет grace/replay recovery.
- Отсутствующие expiry/refresh поля не заменяются выдуманными сроками. Поведение
  определяется полученной и проверенной выдачей, а не догадкой о настройке App.

## Требования и истории

Все R1–R9 обязательны. Архитекторы независимо выбирают схему, блокировки,
формат хранения, порядок durable операций и швы тестирования; PRD задаёт
наблюдаемые результаты, а не конкретный технический schema.

| ID | История пользователя | Требование |
|---|---|---|
| R1 | Я уже вошёл; обновление утилиты не должно выкидывать меня. | Существующий действующий долгоживущий токен продолжает работу без нового входа, нового серверного grant или отказа из-за отсутствия refresh/expiry. Совместимость и сохранность текущего входа обязательны; при изменении локального формата переход безопасен и не требует браузера. |
| R2 | Если GitHub выдаёт короткий access, я не хочу входить каждые несколько часов. | Полученные refresh и сроки сохраняются надёжно; access автоматически продлевается и новая выдача используется при следующих запросах. Каждая нормальная ротация проходит без device flow/browser/подтверждения. Продление после issuer TTL также доступно при пробуждении, если refresh ещё действителен. |
| R3 | Я закрываю ноутбук на недели и возвращаюсь к работе. | После сна/restart приложение заново оценивает срок и зависимости, автоматически восстанавливает доступ и синхронизацию. Нет требования продлевать во сне. После доступности сети и хранилища при работающем приложении восстановление начинается в ближайшую автоматическую попытку, не позднее 10 минут; конечный сетевой запрос ограничен timeout. Не требуется вручную нажимать «Обновить» или входить. |
| R4 | Wi-Fi пропал или KWallet/Keychain запускается позже приложения. | Offline, timeout, 429/5xx, locked/unreachable и временная ошибка чтения/записи сохраняют последнюю безопасно сохранённую авторизацию. Повторные попытки ограничены, UI отзывчив, нет сетевого/диалогового шторма. Разблокировка/возврат сервиса позволяет продолжить автоматически; ошибка доступа не подменяется отсутствием записи. |
| R5 | Приложение перезапускается, CLI и GUI могут работать рядом. | Один issuer refresh не расходуется конкурирующими локальными процессами; новая пара и её принадлежность входу доступны после restart. Запоздалый ответ/ошибка старой операции не перезаписывает и не удаляет более новый вход. Смена аккаунта не смешивает расход и авторизацию разных пользователей. |
| R6 | Я нажал «Выйти» на одном компьютере. | Local-only logout сохраняется: локальные access/refresh и допустимые локальные копии удаляются по прежним гарантиям очистки, серверные grant и другие компьютеры не отзываются. Незавершённое продление/вход не воскрешает отключённую сессию. Повторный вход возможен только по явному действию. |
| R7 | Реальная причина сбоя должна быть понятна. | RU/EN Settings/main различают восстановление, недоступность storage/network, действительно отсутствующий ключ и необходимость нового входа. Истёкший access при рабочем refresh не объявляется окончательной утратой входа. Missing Keychain не утверждает серверный отзыв. Подтверждённый невосстановимый отказ показывает объяснение и одно явное действие входа; приложение не запускает его само. |
| R8 | Продление не должно раскрывать ключи. | Access/refresh и любые секреты хранятся в допустимом защищённом локальном хранилище; не в prefs, gist, stdout/логах, argv или UI. Допустимы безопасные локальные метаданные сроков/статуса без credential values. Нет нового plaintext fallback только потому, что secure storage временно недоступно. |
| R9 | Ошибка или сбой процесса не должны уничтожать известный рабочий вход. | Неполный/ошибочный ответ, ошибка сохранения или локальная конкуренция не публикуют смешанную пару и не удаляют действующие credentials. Уже надёжно сохранённый результат восстанавливается после crash. Необратимая неопределённость между приёмом refresh issuer и durable сохранением новой пары обработана честно, без бесконечного reuse и без обещания невозможного восстановления. |

Срок 10 минут — предел начала автоматического восстановления при здоровых
зависимостях, а не требование сократить до этого любую санкцию issuer. Если
действует `Retry-After`/rate limit, следующий шаг следует разрешённому issuer
сроку и объясняется в статусе. Изменение автообновления Claude/Codex и его кнопки
не используется как средство исправить независимый GitHub lifecycle.

## Авторизация и окончательный отказ

Сохраняется выбранная пользователем тройная проверка 401 перед классификацией
действительно недействительного доступа. Поддержка refresh должна отличать
истечение восстанавливаемого access от окончательного отзыва: доступная
автоматическая возможность восстановления используется до требования ручного
входа и разрушения credentials. Точный порядок refresh/401 и адресной очистки
предлагают архитекторы; случайный non-401, сетевая ошибка или закрытое хранилище
не превращаются в окончательный отказ.

Если сохранённый access уже истёк и предыдущая версия не сохранила refresh,
может потребоваться **один** явный вход для получения полной новой выдачи.
После него здоровый lifecycle соответствует R2. То же относится к реально
отозванному/истёкшему refresh. Это отдельные терминальные fixtures, а не
разрешение показывать повторный вход на каждый временный сбой.

После неоднозначного refresh-ответа сначала используются только допустимые
доказанные способы восстановления issuer/сохранённого состояния. Нельзя
объявить серверный отзыв только по timeout. Если старая одноразовая выдача уже
расходована, ответ утрачен и recovery issuer не существует, приложение ясно
объясняет невозможность автоматического продолжения; нужен один явный вход.
Внешние правила GitHub и реальные server revocations не контролируются клиентом.

## Приёмка на синтетическом lifecycle

Критерии выполняются **на обеих платформах**, с fake issuer/storage/часами и
без доступа к реальным credential files, keyring/DBus, логам пользователя или
GitHub API. Дни симулируются; ожидание полугода в реальном времени не требуется.
Доказательства состояния, операций и авторизованного расхода независимы от UI.

| ID | Сценарий | Обязательные наблюдения |
|---|---|---|
| A1 | Рабочая короткая выдача с issuer TTL; последовательная работа 30 и 180 simulated дней | На всём горизонте проходят авторизованные sync; ротаций достаточно для покрытия срока. После единственного исходного подключения new device-flow=0, browser/confirmation=0, необоснованной потери входа=0. Количество refresh следует TTL, не жёстко зашитым 8 часам. |
| A2 | Уже сохранённый долгоживущий access без refresh/expiry; 30/180 дней и restart | Авторизованные sync продолжаются; refresh/device-flow=0, токен не удалён/не заменён лишь ради новой модели. |
| A3 | Sleep 2 и 6 недель; access истёк, refresh действителен; затем wake/restart | Автоматическое продление и успешный sync после восстановления зависимостей в пределах R3, без пользователя. Долгоживущий вариант тоже восстанавливается. Во сне нет фоновой активности и ложного накопления неудачных попыток. |
| A4 | Offline, transport timeout, 429/5xx; затем нормальная сеть | Не теряется последняя безопасно сохранённая выдача; finite retry/backoff, после восстановления — доступный автоматический sync. Разделить запрос, точно не принятый issuer, и неопределённый исход одноразового refresh; второй проверяется по A9. |
| A5 | SS отсутствует при старте; Keychain/SS locked/read timeout; затем сервис отвечает; отдельно отказ записи нового результата | Нет нового входа/device flow и разрушения auth только из-за временного доступа. Отображается причина, не revoked/missing по догадке; после восстановления продолжается рабочая сессия. Для отказа записи доказать сохранность уже durable данных и recovery по принятому архитектурному контракту. |
| A6 | Два процесса одновременно продлевают один локальный вход; несколько чередований победителя; restart между ними | На каждом шаге одна согласованная актуальная выдача; нет двойного расходования одноразового refresh, смешивания пары или удаления нового результата старой операцией. Проверять также lock timeout и смерть владеющего процесса. |
| A7 | Две машины с независимыми выдачами; обычные renew на одной, local logout на другой; отдельный explicit новый вход | Нет копирования credentials через sync/gist и отзыва доступа другой машины клиентом. Logout не создаёт новый grant; запоздалые renew не восстанавливают локально отключённую сессию. |
| A8 | Crash до запроса, после durable сохранения, перед публикацией; late response после logout/смены аккаунта | Recover сохраняет соответствующий актуальному входу результат; сохранённая новая выдача используется после restart, старый ответ не воскрешает/не подменяет сессию. Архитектурный тест-план перечисляет все существенные окна, а не только happy path. |
| A9 | Issuer уже израсходовал refresh, но ответ потерян/процесс умер до durable сохранения; fake issuer без grace | Невосстановимый случай не считается healthy A1. Ограниченные допустимые попытки и честное объяснение; без автоматического device flow/секретов/цикла ручных входов. При explicit новом входе с рабочей выдачей дальнейший A1 проходит. Возможный issuer grace проверяется отдельно, не предполагается. |
| A10 | Refresh реально revoked/expired; expired access без refresh; настоящий triple401; missing локальной записи | Ровно понятное требование одного явного входа, корректная классификация причин и прежние адресные гарантии очистки. Temporary ошибки не попадают сюда; срок нового refresh не выдумывается. |
| A11 | Отсутствующие/неполные expiry поля, неполная пара, неожиданный issuer error; clock rollback/скачок вперёд | Не теряется действующий вход, нет смешанной выдачи и бесконечного/busy-loop retry. Работоспособный long-lived ответ совместим; срок короткой выдачи берётся из проверенных issuer данных. Поведение не зависит от not-due предположения в тесте. |
| A12 | RU/EN, Settings/main: нормальный доступ, renewal, temporary storage/network, terminal failure | Текст, actual controls/hits и безопасные bitmap соответствуют состоянию. В здоровых A1–A8 login affordance не подменяет recovery; в терминальном случае понятно явное действие. Cache расхода сохраняется и не маскируется как свежее успешное чтение. |

Для A1/A2 число операций и marker успешной авторизованной синхронизации
обязательны; проверка одного formatter или сохранённого login недостаточна.
Секреты представлены синтетическими sentinel, подтверждается их отсутствие
в prefs/gist/logs/argv/UI и невозможность обращения к реальным backend.
Все уже существующие 401, поколения, logout и изоляция остаются обязательной
регрессией. Недоступные GUI/интеграционные проверки отмечаются как непроверенные;
skip или старый релизный PASS не доказывает новый auth lifecycle.

## Границы и решения до production

Входит: поддержка полных выдач по issuer fields, автоматическое продление,
безопасная локальная долговечность, конкуренция, восстановление после сна и
недоступного storage/network, честное представление причин на обеих платформах.
Не входит: менять OAuth App глобально, отзывать все grant пользователя, переносить
credentials между компьютерами, менять local-only logout, вводить облачный
credential proxy, гарантировать отсутствие внешних GitHub revocations.

Продуктовые развилки для координатора после двух независимых архитектур:

1. При новом **явном** входе возможен runtime opt-in для получения refresh, если
   issuer поддерживает его. Предпочтение — получить способность к автоматическому
   продлению при первом входе без изменения действующих long-lived сессий.
   Сохранить минимальные permissions; решение о параметрах и совместимости
   принимается по официальному контракту, без глобальной настройки чужого App.
2. Для одноразового refresh нужно явно принять документированную границу A9;
   невозможное восстановление без issuer grace не скрывается обещанием «полгода».
   Если архитектура вводит дополнительный recovery-протокол или внешнюю службу,
   это отдельный существенный продуктовый выбор, не молчаливое расширение.
3. При временно закрытом защищённом storage сохраняется обычный запрос разблокировки
   ОС, когда необходим; он не является повторной GitHub-авторизацией. Автоматическое
   browser/device подтверждение для нормального renew не допускается.

Нет обязательного вопроса пользователю, препятствующего универсальной локальной
реализации. Данные о его машине нужны для точного диагноза и live-проверки,
но не заменяют архитектуру/приёмку. Для конкретной версии OAuth API/платформы
неподдерживаемая выдача описывается как ограничение, без выдуманного refresh.

## Готовность к выпуску

Координатор сводит две независимые архитектуры и фиксирует accepted lifecycle;
тест-план уточняется до production. Затем отдельные Developer, Tester,
CodeReviewer/Security и QA проверяют exact freeze. Проверки должны доказать
клиентскую устойчивость A1–A12, сохранить прежние регрессии и отдельно отметить
issuer/environment ограничения. Живые credentials/accounts не нужны для
synthetic приёмки; реальный диагноз и полугодовое наблюдение не заявляются
выполненными по симуляции.
